## 0. 目的

**同じ種類の音源が複数載った構成を、ミキサーで個別に扱えるようにする**（2026-10-18 ユーザー指示）。
実機ではスロットやポートが競合しない限り同じデバイスを複数載せられる（SCC カートリッジ 2 本、
MSX-MUSIC 内蔵機に FM-PAC、Y8960 2 枚など）。現状のミキサーはこの構成を表現できない。

GUI の手直しではなく、**仕組みそのもの**（チャンネルの登録・識別・設定の保存・画面）を作り直す。

## 1. 現状

すべて **確認済み(読解)**。行番号は 2026-10-18 の `feature/y8960`（`9e6322f9`）。

### 1.1 合成部 `Src/SoundChips/AudioMixer.{h,c}`

- チャンネルは `mixerRegisterChannel(mixer, audioType, stereo, cb, rateCb, ref)` で登録する。
  **渡すのは種別（`MixerAudioType`）だけで、どの個体かを表す情報は無い**（`AudioMixer.h`）
- 音量・パン・有効は**種別ごとに 1 組**（`AudioTypeInfo audioTypeInfo[MIXER_CHANNEL_TYPE_COUNT]`）。
  `mixerRecalculateType` が同じ種別の全チャンネルに同じ値を配る（`AudioMixer.c` の `mixerRecalculateType`）
- レベルメーターも種別単位。`mixerGetChannelTypeVolume` は同じ種別のチャンネルの**最大値**を返す
- **チャンネルは 15 本まで。** `MAX_CHANNELS` は 16 だが、判定が `channelCount == MAX_CHANNELS - 1`
  なので 16 本目は入らない。**溢れると handle 0 が返り、そのデバイスは黙って鳴らない**
  （`mixerRegisterChannel`）。呼び出し側で 0 を見ている箇所は数えていない
- **MIDI の扱いに潜在的な誤りがある。** `mixerRecalculateType` は MIDI のとき
  `mixer->channels + MIXER_CHANNEL_MIDI`、つまり**登録順で 10 本目のチャンネル**に MIDI の
  音量・パン・有効を書き込む（本来は `mixer->midi` に書くべきところ）。`updateVolumes` も
  `channels[MIXER_CHANNEL_MIDI]` を MIDI の音量として読む。10 本目が PSG〜IO（種別値 0-8）なら、
  全種別の再計算（マスター音量・ステレオの切り替え）のたびに MIDI の設定で上書きされる。
  上流 `develop` の同じ箇所も同じ（`git show upstream/develop:...AudioMixer.c` の 164 行・331 行）。
  **確認済み**: `tests/mixer-probe.c` で、PSG を 10 本登録して MIDI を切ると 10 本目だけ 0 になった
  （直す前の `upstream/develop` `475dadfa` で 1 本目 234 / 10 本目 0）。
  **実際の機種で 10 本以上が登録されるかは数えていない**（未確認。起動した機種で `channelCount` を出せば決まる）。
  段取り 1 で直した（§5）

### 1.2.1 個体の場所はどこで分かるか

生成箇所を全部調べた（2026-10-18。調べたのは補助のエージェントで、要点は下の通り。
**確認済み(読解)** と書いた行は自分でも読んだ）。

- **場所を知っているのは、マッパーの生成関数を呼ぶ 2 か所だけ。**
  機種の構成から作る `Board/Machine.c` の `machineInitialize`（`slotInfo[i]` の
  slot / subslot / startPage）と、カートリッジを挿す `Memory/MegaromCartridge.c` の
  `cartridgeInsert`（`cartNo` と slot / sslot）
- マッパーの多くは slot / sslot / startPage を引数に受けるが、**音源の生成関数には渡していない**。
  I/O だけのマッパー（MoonSound、Joyrex PSG、Opcode PSG、turbo R PCM、Y8960 の I/O ブロック）は
  場所を引数に持たない
- 本体の装置（PSG、キークリック、カセット、SG-1000 / Coleco / Adam の SN76489）は
  `Board/*.c` が作り、場所の概念が無い
- FDC の動作音（`FdcAudio.c`）は FDC の生成から 2 段下で作られる
- 実行中に作り直すものがある（`PrinterIO.c` の DAC は `printerIoSetType` で作り直す）
- **1 つの生成関数が同じ種別を 2 本作る例は無い。** 同じ種別が並ぶのは、別々の個体のとき
  （カートリッジ 2 本、本体の PSG とカートリッジの AY8910 など）。例外として、SVI は
  キークリックを 2 本登録する（`SVI.c` と `SviPPI.c`）
- Y8960 の 4 ブロックは同じ種別 `MIXER_CHANNEL_Y8960` で登録する。**I/O ブロック 3 つは
  ファイル内の静的変数で 1 つずつしか持てない**（**確認済み(読解)**: `romMapperY8960Opllex.c` 44 行、
  `romMapperY8960Opl2ex.c` 44 行、`romMapperY8960Ssgs.c` 46 行、`romMapperY8960Scc.c` 79 行）
- MSX-AUDIO は個体ごとに I/O の基底（`0xc0 + deviceCount++ * 2`）を持つ
  （**確認済み(読解)**: `romMapperMsxAudio.c` 506 行）
- ミキサーはプロセスに 1 つ。`boardGetMixer()` と `mixerGetGlobalMixer()` は同じものを返す
  （推測: どのフロントエンドも `mixerCreate()` を 1 回だけ呼ぶことからの読み）

### 1.2.2 設定ファイルの読み取りの癖 `Src/Utils/IniFileParser.c`

鍵の形を決める前提になる。

- **読み取りは前方一致である。** `iniFileGetInt` は `strncmp(buff, entry, len)` で探す
  （**確認済み(読解)**: 300 行）。**ある鍵が別の鍵の先頭部分になっていると、先に書かれた方を読む。**
  書き込みは `鍵=` で完全一致を取る（430 行、456 行）ので、読みと書きで一致の仕方が違う
- 数値は `=` の後の先頭の数字だけを読む。負の数と `=` の後の空白は 0 になる（311 行）
- 1 行は 512 文字未満（`IniFileParser.h` の `MAX_LINE_LENGTH`。超えたときの検査は無い）
- 鍵に使える文字の制限は無い

### 1.4 画面

- ミキサー画面は**テーマ**（`ReleaseFiles/Properties/Mixer/theme.xml`）。固定座標のビットマップで、
  ラベルは背景画像 `MixerMain.bmp` に焼き込まれている。開くのは `Win32.c` の `archShowMixer`
- 帯は 11 本（PSG / SCC / PCM / MSX-MUSIC / MSX-AUDIO / MoonSound / SFG / Keyboard / IO / MIDI / Cassette）。
  **`Y8960` と `OPNA_*` には帯が無い**（`bluemsx.ini` を書く以外に変える手段が無い）
- テーマの部品と種別の結び付けは、種別ごとに手書きの関数である。
  - 操作: `Actions.c` の `actionVolumeSet*` / `actionPanSet*` / `actionMuteToggle*`（1613-1685、1856-1962）

## 3. 骨格の案（未検証）

### 3.1 合成部

- チャンネルの登録に**記述子**を渡す。種別（従来の `MixerAudioType` を「群」として残す）、
  個体の場所（スロット・サブスロット、または内蔵・I/O）、個体内の名前（`FM` / `SSG` など）、表示名
- 調整値はチャンネルごとに持つ。実効のゲインは **チャンネル × 群 × マスター**（§4 の 2 で決める）
- 本数の上限を外す（動的配列）。溢れる形を残すなら、少なくとも黙らせない
- チャンネルの増減を外に知らせる（世代番号か通知関数）。画面はそれを見て組み直す
- **場所は、登録の「文脈」としてミキサーに渡す。** `machineInitialize` と `cartridgeInsert` が
  マッパーを作る直前に場所を設定し、直後に戻す。その間に登録されたチャンネルがその場所を持つ。
  文脈の外で登録されたもの（本体の装置、実行中の作り直し）は「本体」になる。
  **音源の生成関数の引数は変えない**（§1.2.1。呼び出しは 65 行あり、場所を知っているのは 2 か所だけ）
- 同じ文脈で同じ種別が 2 本目以降に来たら、登録順の番号を付けて区別する（SVI のキークリック）。
  個体の中の名前を渡したいもの（Y8960 の 4 ブロック）には、名前付きの登録を足す
- 旧来の `mixerRegisterChannel` は引数を変えずに残す
- MIDI の誤り（§1.1）は、上流に出せる単独のコミットで先に直す

### 3.2 識別と保存

個体の設定を次回の起動へ持ち越すには、**同じ個体を同じ鍵で呼べること**が要る。
鍵の作り方は §4 の 3 で決める。種別の既存のキーは群の設定として残し、既存の利用者の
`bluemsx.ini` は壊さない。

### 3.3 画面

§4 の 1 で決める。

### 3.4 種別の表

種別ごとに手で並んでいる箇所（§1.3、§1.4、§1.5）を、種別の表（識別子・ini のキー・
表示名・既定値）1 本から引く形にまとめる。**ini のキーの文字列は今の形を保つ**
（`MIXER_CHANNEL_PSG` など。変えると利用者の設定が消える）。

### 4.2 鍵の形（確定）

```
sound.mix.<種別>.<場所>[.<名前>].<enable|pan|volume>
```

| 部分 | 値 |
|---|---|
| 種別 | テーマが既に使っている短い名前をそのまま使う: `psg` `scc` `pcm` `msxmusic` `msxaudio` `moonsound` `sfg` `keyboard` `io` `cassette`（`ThemeLoader.cpp` の `level-psg` などと同じ）。MIDI はミキサーの音を通らないので個体を持たない。フォーク側で `y8960`、`opnafm` / `opnassg` を足す |
| 場所 | スロットを占めるもの: `slot<基本>-<拡張>`（拡張していないスロットも `-0`）。I/O だけのもの: `board`、ポートで区別できるものは `board-<先頭ポートの 16 進>`（`board-c0`）。本体の装置: `board` |
| 名前 | 個体の中の名前（Y8960 の `scc` / `opll` / `opl2` / `ssg`）。名前が無く、同じ場所に同じ種別が 2 本目以降に来たら `n2` `n3` … |

例:

```
sound.mix.scc.slot1-0.volume=100
sound.mix.scc.slot2-0.pan=60
sound.mix.psg.board.volume=100
sound.mix.msxaudio.board-c0.volume=100
sound.mix.msxaudio.board-c2.volume=100
sound.mix.keyboard.board.n2.enable=yes
sound.mix.y8960.slot1-0.opll.volume=90
```

**前方一致の読み取り（§1.2.2）で取り違えない形にしてある。** どの部分の後にも `.` か末尾の属性名が来るので、
ある鍵が別の鍵の先頭部分になることは無い（`board` と `board-c0`、`slot1-0` と `slot1-1` のどちらも、
次の文字が `.` と `-` / 数字で分かれる）。既存の `sound.mixerChannel.*` とも `sound.mix` の次の文字で分かれる。

**I/O だけのデバイスを board で多重化できるか**（2026-10-18 ユーザーの問い）: できる。区別の印が要り、
**ポートが一番よい印である**（実機で同じ種別が 2 つ載るのは、ポートが別のときだけなので）。ただし今ある
I/O だけのデバイスで 2 つ載せられるのは MSX-AUDIO（`C0h` / `C2h`）だけで、残りはポートが固定か
（MoonSound `7Eh`, `C4h`-`C7h`、Joyrex PSG `F0h`、Opcode PSG `50h`-`52h`、turbo R PCM `A4h`/`A5h`）、
ファイル内の静的変数で 1 つしか持てない（Y8960 の I/O ブロック）（**確認済み(読解)**: 各マッパーの
`ioPortRegister`、`romMapperMsxAudio.c` 506 行・545 行）。したがってポートを渡すのは MSX-AUDIO だけでよく、
他は `board` のまま。ポートを渡さないものが偶然重なっても `n2` で分かれる。

**スロットを占めるかの判定**（未検証）: 登録の文脈（§3.1）の間に `slotRegister` が呼ばれたかで決める。
呼ばれたらその文脈で登録された全チャンネルが物理スロット、呼ばれなければ `board`。
**個体単位で決まる**ので、Y8960 の特殊カートリッジは 4 ブロックとも同じスロットになる
（I/O ブロックだけを `board` にはしない。同じカートリッジの部品だから）。
`SlotManager.c` に数え上げを 1 つ足すことになる（上流のファイルが 1 本増える）。

### 試験

`tests/mixer-probe.c` は本物の `AudioMixer.c` を、周りを差し替えて（`tests/mixer-host-stub.c`）単体で組む。
`sh tests/build-probe.sh <試す木の blueMSX/Src>` で組んで走らせる。窓は出ない。
各チャンネルに一定の値を返させ、1 本ずつ鳴らして混ぜた結果の左の値を読む。比べる相手はいつも 1 本目。

| 項目 | 何を見るか | 判別力（**確認済み**: 壊した版で走らせた） |
|---|---|---|
| midi × 2 | MIDI を切る・MIDI の音量を 0 にしても 10 本目が 1 本目と同じ | 直す前の `upstream/develop` で 2 項目とも NG（10 本目が 0） |
| cap × 6 | 40 本すべてに handle が付く。15・16・40 本目が鳴る。途中を 2 本外しても 40 本目が鳴り、外した 6 本目は黙る | 直す前で 4 項目 NG（handle、16 本目、40 本目 × 2）。32 本で止める版で 3 項目 NG（handle、40 本目 × 2。**16 本目は通る**） |
| lock × 2 | 公開関数がロックを必ず返し、持ったまま取り直さない。差し替えのセマフォが数を数え、0 を下回ったら入れ子 | 返し忘れの版（`mixerGetMasterVolume`）で 2 項目 NG（返し忘れの後に取ると 0 を下回る）。入れ子の版（`mixerSetMasterVolume` の中で `mixerGetMasterVolume`）で「入れ子」だけ NG |

壊した版は作業ツリーの外に置き、`MIXER_C=<壊した版> sh tests/build-probe.sh ...` で組む。
**probe は 1 本のスレッドで回るので、ロックが実際に排他することは見ていない**（数の釣り合いだけ）。

フォーク側（各枝にマージした後）: `y8960` の種別名と 4 ブロックの名前、`opnafm` / `opnassg`。

### 設計の細目（未検証）

- **個体の値はミキサーが持ち、保存値は差し込み口で引く。** ミキサー（`SoundChips/`）は設定（`Emulator/`）を
  知らない。登録のたびに、鍵を渡して保存値を問い合わせる関数を 1 本だけ外から差し込む
- **保存は固定長の配列**（`Properties` は構造体ごと複写されるので、ポインタを持たせない）。
  満杯なら新しい個体は保存されないが、実行中は効く
- **並行性**: 配列を伸ばすと古い領域が解放されるので、ロック無しで配列を読むと落ちうる。
  カートリッジの抜き差しでエミュレータが止まっているかは読んで確かめられなかった（`boardChangeCartridge` と
  `insertCartridge` を読んだが、止める処理は見当たらなかった。見落としの可能性はある）。
  そこで**止まっていなくても壊れない形**にした: 配列を読む公開関数はすべてロックを取る
  （登録・解除・種別の設定・メーターの読み出し・レートの変更、`mixerSync` の混ぜる部分）。
  **`mixerSync` は混ぜた結果を作業用の配列に置いてロックを返し、それから音声ドライバへ渡す**
  （ドライバは待つことがあり、その間画面のスレッドを待たせないため）。ロックは `archSemaphore*`
  （`Arch/ArchEvent.h`）。`mixerSync` は 0 サンプルのときロックを取らずに戻る。
  音源のコールバックの中で `mixerSync` を呼ぶものは無い（**確認済み(読解)**: `SoundChips/` の `mixerSync(` は
  すべて I/O の書き込みかタイマーの経路）ので、入れ子にはならない
- `[config]` 節の列挙は `iniFileGetSection` で読む（§1.2.2 と同じファイルの 380 行。1 行ずつ `\0` で区切って返す。
  バッファに入らない行は黙って捨てるので、十分に大きく取る）
- 言語の文字列は英語で初期化してから各言語で上書きする（**確認済み(読解)**: `Language.c` 135 行以降）。
  英語と日本語だけ足せば、他の言語では英語が出る

### やり直しの値段（推測: §1 で数えたファイル数からの見積もり）

| 後から変えるもの | 波及 |
|---|---|
| 画面の形 | 画面のファイルだけ。合成部と保存は変わらない（§3 の分け方を守る限り） |

## 6. 見送った案

- **テーマ画面を廃止して新しい窓 1 つに置き換える** — 見送り。理由: ユーザー判断で、テーマ画面を
  種別の操作として残すことにした（§4.1 の 1）
- **テーマ形式に帯の繰り返しを足す** — 見送り。理由: テーマの読み込み・トリガー・ラベル描画の
  作り込みが最も重い（§1.4）
- **種別の階層を無くし、個体 × マスターにする** — 見送り。理由: 既存の種別のキーが個体の初期値としてしか
  使えなくなる（§4.1 の 2）
- **個体の設定を機種ごとに保存する / 保存しない** — 見送り（§4.1 の 3）
- **フォーク内だけで作る / 先に上流へ相談の issue を出す** — 見送り（§4.1 の 4）
- **カートリッジの場所を口の番号（`cart1` / `cart2`）で表す** — 見送り。理由: ユーザー判断で、
  スロットを占めるものは物理スロット、I/O だけのものは `board` にした（§4.1 の 5）
- **鍵の種別に既存の識別子（`MIXER_CHANNEL_SCC`）を使う** — 見送り。理由: ユーザー判断で短い名前にした
  （§4.1 の 6）。短い名前はテーマの名前を流用し、名前の体系を新しく作らない
- **個体のパンが種別のパンを上書きする** — 見送り（§4.1 の 7）
