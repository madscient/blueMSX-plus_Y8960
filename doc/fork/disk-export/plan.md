# メモリ上のディスクイメージの書き出し — 計画と経緯

対象読者は開発者と AI。Y8960 とは独立した、ディスク周りの機能。

**動機**: 「ディレクトリ挿入」で挿したディスクは、MSX から書いた内容が
どこにも残らない。イジェクト・リセット・終了のいずれでも消える。

上流候補なので、**`upstream/develop` から切った枝
`feature/disk-image-export` に、コードだけのコミットで作る**
（`doc/fork/README.md` の「上流へ出すとき」）。この文書は上流に出さない。

## 1. 調べて分かったこと（**確認済み(読解)**）

| | |
|---|---|
| ディレクトリ挿入の実体 | `Disk.c` の `diskChange()` が `dirLoadFile()` を呼び、720 KB の FAT12 イメージを `ramImageBuffer[]` に組み立てる |
| 書き込みは拒否されていない | `diskWrite()` / `diskWriteSector()` の RAM イメージ経路は `memcpy` して成功を返す。`RdOnly[]` も見ていない |
| 消える場所 | `diskChange()` の先頭。`free(ramImageBuffer[...])` の直前に上流から `// Flush to file??` のコメントが残っている |
| リセットでも消える理由 | `Board.c` の `boardRun` 前の復元が、起動のたびにディスクを入れ直す。イメージがホストのディレクトリから作り直される |
| zip 挿入も同じ経路 | `zipLoadFile()` の結果も `ramImageBuffer[]` に入る。書き出しはそのまま効く |
| メニュー ID の空き | ディスクの ID 群は `Win32Menu.c` に直接 `#define` してある。`ID_FILE_DISK_HISTORY` (41305) から `MAX_HISTORY` = 30 本、ドライブ間隔 100 なので、41335〜41399 が空き |
| 翻訳の落とし方 | `langInit()` が各言語を**英語で初期化してから**上書きする。訳を書かなかった文字列は英語になる（NULL にはならない） |
| 保存ダイアログ | `ShellSaveFileDialogEx()`（`Win32FileDialog.cpp`）が既定ファイル名の事前入力に対応している。`SetDefaultExtension` は先頭のドットを取った形を要求する |

## 2. 決まったこと（2026-09-21 ユーザー判断）

| | 決定 | 前提 |
|---|---|---|
| 方式 | **書き戻しではなく書き出し。** RAM イメージをそのまま `.dsk` として出す | ホストのディレクトリを壊す経路を作らないことを優先する |
| メニュー文言 | **「ディスクイメージを書き出し...」**（英語は `Export Disk Image...`） | ディスクメニューの「イジェクト」の下 |
| 書き出した後の差し替え | **しない。** 出すだけ | 以後の書き込みは引き続き RAM に溜まる |
| 書き出さずに消える経路への警告 | **付けない** | 利用者が明示的に書き出す運用 |

### 見送ったもの

- **ホストのディレクトリへの書き戻し** — 見送り。イメージ側の FAT とディレクトリ
  エントリを解釈してホストのファイル群に翻訳し直す必要があり、MSX 側が FAT を
  壊したときにホストのファイルを壊す経路が残る。読み込み時に長い名前を
  `BASE~N.EXT` へ潰している（`DirAsDisk.c` の `msx_assign_short_name`）ので、
  書き戻し先を決めるための対応表も要る
- **書き出し後にそのイメージへ差し替える** — 見送り。`insertDiskette()` を
  1 行呼ぶだけなので、要るようになったら安く足せる
- **未書き出しのままイジェクト・リセットしようとしたときの確認** — 見送り。
  付けるなら文字列が 1〜2 本増える

**引き換えに残る不便**: 出てくるのは `.dsk` なので、MSX で作ったファイルを
ホスト側で個別に取り出すには、もう一度挿し直すか別のツールが要る。

## 3. 作ったもの（`feature/disk-image-export` の 1 コミット）

| ファイル | 内容 |
|---|---|
| `IoDevice/Disk.{h,c}` | `diskHasRamImage()` と `diskExportRamImage()` |
| `Emulator/Actions.{h,c}` | `actionDiskExport()`。suspend → ダイアログ → 書き出し → resume |
| `Arch/ArchFile.h`、`Win32/Win32.c` | `archFilenameGetSaveDisk()`。既定名は挿してあるディレクトリ名（zip なら中のエントリ名） |
| `Arch/ArchDialog.h`、`Win32/Win32.c` | `archShowDiskExportFailedDialog()` |
| `Win32/Win32Menu.c` | `ID_FILE_DISK_EXPORT` (41340)、メニュー項目、ディスパッチ |
| `Language/` | `menuDiskExport` / `dlgSaveDisk` / `errorDiskExportFailed` を 16 言語ぶん |
| `Sdl/`、`Linux/blueMSXlite/` | 空のスタブ 2 本ずつ |

メニュー項目は RAM イメージを持たないドライブでは灰色になる。

**英語と日本語以外の訳は推測。** 根拠は同じ意味の既存文字列の言い回しだけで、
各言語の利用者に確かめていない。

### 確度

- **確認済み**: ビルドが通ること。`msvc2022` の `blueMSX.sln` を
  `Configuration=Debug;Platform=x64` で MSBuild にかけ、終了コード 0。
  リンクまで到達している
- **未検証**: 実際に書き出した `.dsk` が正しいこと。エミュレータを起動して
  ディレクトリを挿し、MSX から書いてから書き出し、その `.dsk` を挿し直して
  中身が読めることを見ていない

Release 構成のリンクは、その出力先の実行ファイルが起動中で開けず落ちた
（`LNK1104`）。コンパイルは全ファイル通っている。

## 4. 次に確かめること

1. ディレクトリを挿す → MSX-DOS から `SAVE` → 書き出し → その `.dsk` を挿し直して
   ファイルが読めるか
2. 書き出し先を書き込めない場所にして、失敗のダイアログが出るか
   （**この確認をするまで、失敗経路は「通ったことがない」**）
3. zip から挿したディスクでも書き出せるか
4. ディスクを挿していないドライブでメニュー項目が灰色になるか
