# doc/fork/ai — AI 向けの作業規則

**この階層は AI が読む前提の文書だけを置く。**
上流（Hesoten/blueMSX-plus）は `.gitignore` で `CLAUDE.md` を除外しており、
この種の文書をリポジトリに置かない方針だが、**このフォークでは場所を限定して置く**
（2026-09-12 ユーザー判断）。限定とは次の 2 か所のこと。

| 場所 | 役割 |
|---|---|
| ルートの `CLAUDE.md` | **索引のみ。** 規則の中身は書かない |
| `doc/fork/ai/`（本階層） | 規則の本体 |

人間向けの事実と索引は `doc/fork/README.md`、Y8960 の実装計画は
`doc/fork/y8960/implementation-plan.md`。

**セッションを引き継いだら、まず `y8960/implementation-plan.md` §0 を読む。**
現在地・確かめずに残してあること・次の一手がそこにある。
**「確かめずに残してあること」を確かめ済みとして扱わない。**

## 上流に出すものへ混ぜない

**プルリクエストや issue に、この階層の文書を混ぜないこと。**
上流はこの種の文書を置かない方針なので、送りつける形になる。

上流へ出す枝は `upstream/develop` から切り直し、**コードだけを載せる**
（`doc/fork/README.md` の「上流へ出すとき」）。
`doc/` 配下が差分に入っていないことを、出す前に確かめる。

```sh
# 上流へ出す枝に doc/ が混ざっていないか
git diff --name-only upstream/develop..<枝> | grep '^doc/' && echo "MIXED IN"
```

## 作業の記録と確度

主題ごとに作業計画と実行経緯の文書を持ち、決定・却下・訂正はその都度書く。
Y8960 なら `y8960/implementation-plan.md`。口頭で終えない。

主張には確度を併記する。走らせて確かめたなら**確認済み**とその手段を、
読んだだけなら**確認済み(読解)** とファイル名と行を、作っただけなら**未検証**、
出典を示せないなら**推測**と根拠を一行。

**外に出る値を決める直前に一声かける。** `RomType` の数値、ミキサー種別の
識別子、I/O アドレス、設定ファイルのキー、セーブステートの節名。
これらは後から変えると利用者のファイルに波及する。確定したものは
`y8960/implementation-plan.md` §6 にだけ書く（二重に持つと片方が古くなる）。

### 観測の意味を確かめる

確度を付ける前に、**その観測が主張したい意味を持つか**を確かめる。
観測したこと自体は正しくても、意味の読み違いは残る。

失敗の形は 2 つあり、**どちらも「期待どおりに見えた」ときに起きる**。

| 形 | 問い |
|---|---|
| **何も起きなかった** | その仕掛けは、起きていたら報告できたのか |
| **期待どおりの出力が出た** | その出力は、期待した意味を持つと確かめたのか |

前者は 0 件を証拠にしようとするとき。**測定器に判別力があること**を、
期待を外した条件で 1 度出させて示すまで、0 件は何も語らない。

**判別力が無いと分かったテストは消す。** 直らないまま緑を出し続け、
次に読む者に「ここは確かめてある」と思わせる。
確かめられないなら、**確かめられないことを書く**方が役に立つ。

後者は**他人が作った表示を根拠にするとき**に起きやすい。
エミュレートされた BIOS の画面、ライブラリのログ、ツールの終了コード。
**その表示の仕様を知らないまま解釈しない。**
知らないなら「こう見えた」までを書き、意味の断定はしない。

実例（2026-09-12、どちらも踏んだ）。

- 重なりだけを記録する仕掛けで 0 件を得た。仕掛けが動いていない可能性を
  排除していなかった。全件を記録する形に変えて初めて判別力が付いた
- C-BIOS の `Init ROM in slot:` が 2 回出たことを
  「2 つのバンクが別々に見えている証拠」と読んだ。**標準の MSX BIOS は
  ROM ヘッダを 4000H と 8000H でしか探さない。** この表示が何を意味するかを
  確かめていなかった
- MSX 側から書いて読み返すテストが通ったので、その領域が正しく
  マップされていると読んだ。**アクセスはそもそも対象のデバイスに
  届いておらず**、RAM の同じ場所に書いて読んだだけだった。
  **「往復できた」は「相手に届いた」ではない**

3 つ目が一番たちが悪い。**書いた値がそのまま読めるのは、相手が誰であっても
起きる。** 書いた先と読んだ先が同じであることしか示さない。
届いた先を確かめるには、**その相手にしか持てない性質**を見る
（別の口から同じものが見える、電源投入時の既定値が違う、など）か、
相手の側に記録を仕掛ける。

#### 判別力は、壊した版に掛けて示す

**「直した後に通る」は証拠にならない。** 試験を書いたら、**確かめたい振る舞いを
壊した版を作り、その版で落ちることを見る。** 壊した版は作業ツリーの外に置き、
リポジトリには入れない。落ちた項目の数と名前を文書に残す。

**壊し方は 1 つでは足りない。** 同じ機能でも壊し方によって捕まる項目が違い、
**1 つの壊し方しか試さないと、そこだけ見ている試験が満点に見える。**

**連続した枠は両端を踏む。** レジスタ `40h`-`48h`、バンク `#0`-`#15` のような
連続した範囲は、真ん中を 1 つ試せば通る。**上限を 1 つ狭めた版は、
端を踏む項目を足すまで捕まらない。**

### コミットの分け方

**フェーズ単位ではなく、論理単位で分ける。** フェーズは作業の区切りであって、
変更の論理単位ではない。Phase 0 が 1 コミットで済んだのは「器を作る」という
単一の論点だったからで、途中で切ると中途半端な状態が残るためである。

**上流に出せる変更は、必ず単独のコミットにする。**
2026-09-12 に IoPort の多重化を Y8960 の文書と同じコミットに入れてしまい、
上流へ出すときに**別ブランチで書き直す**ことになった。
最初から分かれていれば cherry-pick で済んだ。

| 変更の種類 | 置き場所 |
|---|---|
| 上流のバグ修正・上流に還元できるもの | **単独のコミット。** `upstream/develop` から切り直せる形に |
| Y8960 固有の実装 | 機能ごとに 1 コミット。各コミットでビルドが通ること |
| 設計を説明する文書 | **対応するコードと同じコミット**（なぜそう作ったかが一緒に残る） |
| 実測結果・経緯の追記 | **別コミット**（後から分かったことなので） |

### 設計を決める前に、移植元の同じ箇所を見る

**この移植には先行実装がある**（madscient/openMSX_Y8960）。同じハードウェアを
同じ人が実装しており、**設計上の分かれ道はあちらで一度通過している。**

したがって、ブロックの作りを決めるときは**先に openMSX_Y8960 の対応箇所を
読む。** 違う結論を出すなら、なぜ違えるのかを `implementation-plan.md` に書く。

**保守コストだけで決めない。** 「上流のコアを共有すれば上流の修正がそのまま
効く」は正しいが、それは**モデルとして正しいかとは別の軸**である。
Y8960 の音源ブロックは本体のチップそのものではなく等価回路なので、
共有すると挙動が分岐したときに表現できない（§11 の 2026-09-12 (10)）。

判断の前に次の 2 つを分けて書く。片方しか書けないなら、まだ決められていない。

- **モデルとして正しいか** — 実物の何を写しているか。別物なら別に持つ
- **保守コストはどうか** — 追従の手間、衝突面の大きさ

**ハードウェアが WIP である間は、モデルの正しさが優先する。**
仕様が動いたときに、分けてあるものは分岐を書けるが、
共有したものは作り直しになる。

## ヒアドキュメントにバックスラッシュを書かない

**この作業ツリーでは、Bash ツールのヒアドキュメントがバックスラッシュを
1 段消費する。** スクリプトが読む前に `\\` が `\` になり、`\b` が
バックスペース文字 (0x08) になる。

**黙って通る。** 片方は「アンカーが一致しない」で止まるので気づけるが、
もう片方は**不可視の制御文字を成果物に書き込んで成功する**。
`sed -n` で読み返しても `$dir` と `blueMSX+.exe` が繋がって見えるだけで、
何が起きたか分からない。

したがって次のようにする。

- **バックスラッシュを含むスクリプトは、ヒアドキュメントで渡さない。**
  Write ツールでファイルに書き、そのファイルを実行する
- どうしても要るなら `chr(92)` で組み立てる。文字として書かない
- **Windows のパスや PowerShell の断片を文書に埋めるときは、書いた後に
  `grep ... | cat -A` で読み返す。** 制御文字は `^H` のように見える

同じ理由で、`\r` `\t` `\n` も文字として書かない。

**危ないのは渡すスクリプト自身ではなく、その中の文字列リテラルである。**
Python を渡すときは Python のコードにバックスラッシュが無くても、
書き込む中身（C のエスケープ、Windows のパス、正規表現）に在れば同じ目に遭う。

**書き終えたファイルは、目で読まずに走査する。** 触ったファイルを列挙して
制御文字の有無を出す。1 件でも出たら、その場で直してから次へ進む。

```sh
python -c "
import sys
bad = set(range(0,32)) - {9,10,13}
for f in sys.argv[1:]:
    hits = [(i,b) for i,b in enumerate(open(f,'rb').read()) if b in bad]
    print(('%-56s ' % f) + ('clean' if not hits else 'CONTROL CHARS %s' % hits[:5]))
" <触ったファイル...>
```

## 出す前に

`origin` は GitHub にある。**push したオブジェクトは親リポジトリから SHA で
辿れて、後から消せない。** 点検は push の前にしか意味が無い。

- **ローカル固有のパスが混入していないか。** 成果物にもコミットメッセージにも
  書かない。スクリプトでパスが要るときは環境に依存しない形にする
- **個人情報が混入していないか。** 成果物にもコミットメッセージにも書かない
- 未コミットの変更が残っていないか
- ビルドが書き換えた `Src/BuildInfo/` の 2 本を戻したか（`build/README.md` §2）
- 文書の索引と実体が食い違っていないか

**push の残りを数えるときは追跡ブランチと比べる。** 比較先を決め打ちにしない。
作業ブランチは `main` とは限らず、`main` と比べると上流同期分まで数に入る。

```sh
git rev-list --count @{u}..HEAD     # 追跡ブランチとの差
git rev-parse --abbrev-ref @{u}     # 比較先の名前を人に伝える
```
