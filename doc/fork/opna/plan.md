# Makoto（YM2608 OPNA カートリッジ）対応 — 計画と経緯

対象読者は開発者と AI。Y8960 とは独立した、音源カートリッジの追加。

上流候補なので、**`upstream/develop` から切った枝 `feature/makoto-opna` に、
コードだけのコミットで作る**（`doc/fork/README.md` の「上流へ出すとき」）。
この文書は上流に出さない。

## 1. 調べて分かったこと

### 1.1 Makoto のハードウェア

出典は VGMPlay MSX の Makoto ドライバ（sharksym/vgmplay-sharksym の
`src/drivers/Makoto.asm`）。**確認済み(読解)**。製品ページ（Supersoniqs）と
MSX Resource Center の開発スレッドには I/O の記述が無い。

| | |
|---|---|
| チップ | YM2608 (OPNA) + YM3016 (DAC) |
| クロック | 8 MHz |
| I/O ポート | `14h` 表アドレス / 表ステータス、`15h` 表データ、`16h` 裏アドレス / 裏ステータス、`17h` 裏データ |
| 表（`14h`/`15h`） | FM 1–3ch、SSG、リズム（ADPCM-A）、共通レジスタ |
| 裏（`16h`/`17h`） | FM 4–6ch、ADPCM-B |
| ADPCM-B のメモリ | ドライバは **1bit DRAM モード**（裏 `01h` の bit1 = 0）に設定する。アドレスは 4 バイト単位 16bit なので上限 256 KB |
| `14h` の読み | ドライバは読まない。コメントに「Music Module とバスが衝突する」とある |
| 検出 | 裏 `00h` に `80h`（START）を書き、裏ステータスの bit5 が立つことを見る |

**利用者から得たこと**（2026-09-22）: ADPCM-B の RAM は **256 KB**、
**/IRQ は MSX の /INT に繋がっている。** どちらもドライバからは決まらなかった
（ドライバは容量を調べず、割り込みを切って使う）。

**未確認**: `14h` の読みで何が返るか（本物のステータスか、衝突で不定か）。

### 1.2 ymfm

GitHub の aaronsgiles/ymfm、`81aec25ccb`（2026-07-27）時点。**確認済み(読解)**。

| | |
|---|---|
| ライセンス | BSD-3-Clause（GPLv2 と両立する） |
| OPNA の実装 | `ymfm_opn.{h,cpp}` の `ym2608` |
| 依存 | `ymfm.h`、`ymfm_fm.{h,ipp}`、`ymfm_adpcm.{h,cpp}`、`ymfm_ssg.{h,cpp}` |
| 同居しているもの | `ymfm_opn.cpp` には OPN / OPNB / OPN2 系の他チップも入っている |

**ymfm がホストに任せているもの**（`ymfm_interface` の仮想関数）:

| | ymfm の口 | blueMSX 側で要るもの |
|---|---|---|
| リズムの波形 ROM（8 KB） | `ymfm_external_read(ACCESS_ADPCM_A, …)` | 利用者が置くファイルを読む（§2） |
| ADPCM-B の RAM | `ymfm_external_read/write(ACCESS_ADPCM_B, …)` | カートリッジが持つバッファ |
| タイマ A / B | `ymfm_set_timer` | ボードのタイマに繋ぐ。**割り込みを使わないソフトもステータスのフラグで待つ**ので要る |
| IRQ | `ymfm_update_irq` | 繋ぐかどうかは §1.1 の未確認事項による |
| 出力 | `generate()` は FM と SSG を共通のレートに揃えて返す。FM は 8 MHz / 144 ≈ 55.6 kHz、SSG は 8 MHz / 32 = 250 kHz で作られ、別々に回す口は `ym2608` の protected メンバー | それぞれをミキサーのレートへ変換する（§4.5） |

`ym2608::reset()` はリズム 6 音の開始・終了アドレス（`0000h`–`1FFFh`）を
自分で設定する。ROM の中身だけを渡せばよい。

### 1.3 リズム ROM

MAME は YM2608 の内蔵 ROM を `ym2608_adpcm_rom.bin`（8 KB、CRC32 `23c9e0d8`）として扱う
（`src/devices/sound/ymopn.cpp`、**確認済み(読解)**）。中身は YM2608 のマスク ROM の
吸い出しで、**再配布できない**。

### 4.1 作りの要点

| | どうしたか | なぜ |
|---|---|---|
| 生成 | `ym2608::generate()` は使わない。`ym2608` を継承した `Ym2608Chip` から FM+リズム+ADPCM（ステレオ）と SSG を別々に回す。レートは clock ÷ (24 × プリスケーラ) と clock ÷ 32 / 16 / 8 で、8 MHz・プリスケーラ 6 なら 55,556 Hz と 250,000 Hz | `generate()` は 2 つを共通のレートに揃えるために同じ値を繰り返す。経緯と測定は §4.5 |
| レート変換 | ストリームごとに窓付き sinc。ミキサーのサンプルがチップのサンプルの間のどこに落ちるかは、`clock` 対 `sampleRate × 1 サンプルのクロック数` の整数で数える | 誤差を貯めない。高域のレベルと、変換で混ざる成分の測定は §4.5（人が聴いての評価はしていない） |
| ミキサーへの出し方 | FM+リズム+ADPCM をステレオの 1 チャンネル（種別 `MIXER_CHANNEL_OPNA_FM`）、SSG をモノラルの 1 チャンネル（`MIXER_CHANNEL_OPNA_SSG`）として出す。SSG は 3 声の和 × 2/3 | 実機の FM と SSG の比は基板のミキサー回路で決まり、チップの性質ではない。種別を分けたので、利用者が比を変えられる（§4.7）。2/3 は `generate()` が 1 本に混ぜるときの係数で、**実機の値ではない**。両方の種別が既定値のとき、分ける前（L = FM_L + SSG、R = FM_R + SSG）と同じ釣り合いで鳴る |
| 出力の倍率 | 2 倍 | ミキサーは音量 1024 を掛けて 4096 で割る。フルスケールの OPNA がミキサーの約半分になる（**推測**: 他の音源との音量の釣り合いは聴いていない） |
| タイマ | ymfm が求めるクロック数をボード時間に換算して `boardTimerAdd`。**満了から再設定されるときは、予定時刻から数える** | ボードは命令の切れ目でタイマを発火するので、コールバックは遅れる。発火時刻から数えると周期が伸びる |
| ビジー | ymfm が求めた終了時刻をボード時間で持つ | |
| レジスタ書き込み・読み出し | 前に `mixerSync` | 音の生成を書き込み時刻まで進めてから状態を変える |
| peek | 表ステータスだけ返し、他は `FFh` | 裏ステータスの読みはフラグを書き戻し、裏データの読みは ADPCM-B のアドレスを進める（`ymfm_opn.cpp` の `read_status_hi` / `read_data_hi`） |
| ROM が無いときのリズム | ymfm に `08h` を返す | ニブル 0 と 8 が最小の段を足して引くので、アキュムレータは 0 と 2 を行き来するだけになる（`ymfm_adpcm.cpp` の `clock` の復号）。`00h` を返すとずれて行く（§4.2 の b05） |
| デバッガのレジスタ表示 | 書き込みを自前で控える | ymfm はレジスタを外に出していない |
| セーブステート | ymfm の `save_restore` のバイト列と**その並びを示す番号**、タイマ、ビジー、2 本のストリームのクロックの端数と変換器が持つサンプル、ADPCM-B の RAM、レジスタの控え | ストリームの分は、保存したときとミキサーのレート・大きさが同じときだけ戻す。違えば頭から始める（§4.5）。並びの番号が今と違うステートは、ADPCM-B のチャンネルだけを初期状態にする（§4.6） |

### 4.2 確かめたこと

**ビルド**（**確認済み**）: msvc2022 の Release / x64 で 0 エラー。追加したファイルからの
警告は 0 件（6 件の警告はすべて触っていない既存ファイル）。`blueMSX+.exe` は別の実行中の
プロセスが掴んでいたので、リンク先だけを `-p:OutDir=` で作業ツリーの外に変えた。

**登録**（**確認済み**）: そのビルドの `/listspecials` に `MAKOTO  Makoto` が出た（56 行中）。
**`/listromtypes` には出ない** — ROM イメージに掛けるマッパーの一覧で、Joyrex PSG も出ない。
Makoto の登録を確かめる手段にはならない。

**ホスト上の probe**（`tests/opna-probe.cpp`、**確認済み**）: `YM2608.cpp` と ymfm を
エミュレータから切り離してスタブと組み、48 項目がすべて OK（2026-10-04、`f7a4d0f8`。
`2ade339f` の時点では下の表の「セーブしてロード」までの 21 項目、`588325e5` では 38 項目）。
スタブは時間を進められ、ボードタイマを命令の切れ目の遅れ（30 µs）込みで発火する。
ミキサーのスタブは、登録されたチャンネルをすべて呼んで足し合わせる（モノラルは左右の両方へ）。

**ビルドの出力は作業ツリーの外に向ける。** `build-probe.ps1` の `-Out` と `-ObjDir` に
外のパスを渡す。既定のままだと exe と中間ファイルが `tests/` に出て、どちらも gitignore
されていない（**確認済み**: `git check-ignore` が何も返さない）。

| 項目 | 期待値の出所 |
|---|---|
| FM の音程（F-Num 618、BLOCK 4 → 261.94 Hz） | OPN の F-Number の式（**推測**: 記憶による。ymfm からは取っていない） |
| SSG の音程（TP 284 → 440.14 Hz） | clock / (64 × TP)（同上） |
| リズム: ROM 無しで無音、ROM ありで鳴る | ROM ありで RMS 10619.5、無しで 11.4（`588325e5`。`2ade339f` では 10613.6 と 10.4） |
| リズムがひとりでに鳴り終わる（BD 1 打、`opnatest.asm` と同じ BD/SD の並び） | 1〜1.5 秒後の RMS が 0.0 |

### 4.3 試験のときに踏んだこと

- **試験 ROM の誤り**: 最初の版はリズムと区間 5 の回数を E / DE で数え、ループの中で
  `regs`（D と E を壊すと自分で書いた）を呼んでいた。リズムが延々と繰り返され、以降の区間が
  鳴らなかった。ホスト probe で同じ手順が鳴り終わることを確かめてから録音を詳しく見て、
  0 の区間を挟んだ打音の繰り返しだと分かった。回数はメモリに置く形に直した
- **`/romtype1 NORMAL` を付けると ROM が挿さらない。** C-BIOS が「No cartridge found」を出した
  （**確認済み**、画面）。付けなければ挿さる。原因は調べていない（**未確認**）。試験は付けずに走らせる
- 最初の数回は長いパス（約 190 文字）の ROM を渡しており、そのときも無音だった。
  **パスの長さが原因かは未確認**（その実行の画面は撮っていない）。試験は `%TEMP%` の下の短いパスに置く
- 録音が全部 0 のとき、エミュレータが動いていないのか ROM が挿さっていないのかは録音からは
  分からない。本体の PSG で目印を鳴らす版と、メニューからのスクリーンショットで切り分けた
- **`run-opnatest.ps1` の既定の機種は `MSX2+ - C-BIOS - JP`**（2026-10-04 に変えた）。前の既定は
  リポジトリに無い機種構成で、ほかの環境では存在せず、在る環境でも録音が無音になった（§4.9）
- **無音の録音を見たら、デバイスを疑う前に `bootmark.asm` を走らせる。** 本体の PSG だけで、
  「ROM が呼ばれたら 999 Hz、フレームが 60 回進んだら 1998 Hz」を鳴らす。無音なら ROM に制御が
  来ていない。`opnatest.asm` はどちらにも頼っている（`make-opnatest.py <pasmo> <出力> bootmark.asm` で組む）
- **画面はウィンドウを出さずに撮れる。** `/hidden` で走らせ、メニューのコマンド 40017（スクリーンショット）を
  送ると、`/rootdir` の下の `Screenshots/` に PNG が出る（**確認済み**）

### 4.4 確かめずに残してあること

- マシン構成のスロットに置いた場合（特殊カートリッジとしては挿した）
- 実機のソフト（VGMPlay MSX など）での再生
- 音量の釣り合い、レート変換の音質（人が聴いていない。§4.5 の測定は数字だけ）
- **エミュレータの中での** ADPCM-B の再生と転送（ホストの probe では確かめた。§4.6。試験 ROM に ADPCM の区間が無い）
- PR #40 が変えた ADPCM-B の挙動のうち、probe の項目に無いもの（ダミーリード、読みすぎ・書きすぎたときの挙動、PLAYING のフラグ）
- ミキサー画面に `MIXER_CHANNEL_OPNA_FM` / `_SSG` が出ないこと（**確認済み(読解)**: 画面とテーマに何も足していない。画面を開いて見てはいない）

- エミュレータを普通に終了したとき、`bluemsx.ini` に新しい 6 行が書かれること（**確認済み(読解)**: 書き出しの行を足した。試験はプロセスを止めて終えるので、書かれたファイルは見ていない）
- 実行中にプリスケーラを切り替えた瞬間の音（変換器のサンプルを捨てるので途切れうる。音程が追従することは確かめた）

- 公開済みの `v3.1.1-makoto.2` で実際に保存したステートを `588325e5` で読むこと（古い形のステートを**模した**版では読めた。§4.5）
- OPNA の割り込みを許可しながら処理ルーチンを持たないソフトの挙動（実機と同じく割り込みが止まらなくなるはず）
- FM と SSG の期待値の式が YM2608 の原典と一致すること（記憶による。エミュレータとホストで一致しているが、どちらも ymfm なので独立ではない）
- `gcc/Makefile` と msvc2026 でのビルド

### 4.5 FM と SSG を実レートで回す（2026-10-04、`588325e5`）

**発端**: openMSX の upstream に、別の作者による Makoto の実装が PR として出ている
（https://github.com/openMSX/openMSX/pull/2209）。そのレビューで、ymfm の `generate()` に由来する
負荷と音質の問題が指摘された。利用者の指示で、こちらに当てはまるかを測り、対策を入れた。

議論の詳しい記録は、姉妹フォーク madscient/openMSX_Y8960 の枝 `makoto-native-rate` の

#### こちらに当てはまるか

修正前の `b2d4d185` を測った（**確認済み**: `opna-probe.exe` の判定と `--survey`。Win10 機）。

- **負荷**: 当てはまり方が違う。こちらは最初から `OPN_FIDELITY_MIN`（clock / 48）を選んでいたので、
  PR で問題になった 1 MHz の生成は**もともと無い。** 姉妹フォークの測定でも、実レートは MIN と同程度だった
- **音**: 当てはまる。**ymfm の繰り返しに、こちらのグルーの平均が重なっていた。** `generate()` は
  FM の 1 サンプルを 3 回繰り返し（MIN、プリスケーラ 6）、グルーはそれを**整数個**（3 個か 4 個）ずつ
  平均してミキサーの 1 サンプルにしていた。平均の区切りは 6 µs 刻みでしか動かないので、ミキサーの
  サンプルごとに区切りの位置と長さが揺れる。高い音ほどレベルが下がり、元の音に無い成分が混ざる
- **セーブステート**: 当てはまる。プリスケーラ 2 で保存して作り直したチップに読むと、FM が 1/3 の
  音程になった（261.94 Hz、期待 785.83 Hz）。ymfm の状態はプリスケーラを戻すが、`generate()` が
  そこから決める繰り返しの回数は戻さない

**「残り」の測り方**: 音の基本周波数の整数倍と直流を、ナイキスト周波数の手前まで最小二乗で
当てはめ、当てはまった電力と残った電力の比を dB で出す。**音の周期がチップのサンプルの整数個に
なるように選んである**ので、チップ自身の歪みは整数倍に乗り、残るのは変換が足した成分になる。

#### 負荷

`opna-probe.exe --bench`。ymfm とグルーだけを回し、1 秒ぶんの音を作るのに掛かるホストの時間を測る
（30 秒ぶんを 3 回回した最短）。それを版を替えながら 7 巡して、最小と中央を取った（**確認済み**、Win10 機）。
「演奏中」は FM 6 声（アルゴリズム 7、TL 0）と SSG 3 声（音量 15）を鳴らしたまま。鳴っていることは
出力のピークで見た。

| | 無音（最小 / 中央） | 演奏中（最小 / 中央） |
|---|---|---|
| 修正前 `b2d4d185` | 16.75 / 17.03 ms | 29.75 / 31.73 ms |
| sinc 片側 8 | 14.99 / 15.34 | 29.57 / 30.42 |
| **sinc 片側 12（採用）** | 14.97 / 15.51 | 29.88 / 31.06 |
| sinc 片側 16 | 15.18 / 15.68 | 30.66 / 32.44 |

- **無音は約 1 割減った。** 7 巡の範囲は修正前が 16.75〜18.05、採用版が 14.97〜16.07 で、ほぼ重ならない
- **演奏中は差が出ていない。** 1 つの版の中のばらつき（修正前で 29.75〜32.52）の方が、版の間の差より大きい
- 1 コアに対する割合にすると、無音で約 1.5%、演奏中で約 3%。**エミュレータ全体の中での割合は測っていない**
- 残っている負荷は ymfm が FM と SSG を回す分で、無音でも止められない（上の「無音」）

#### 姉妹フォークと違えたところ

| | openMSX_Y8960（`makoto-native-rate`） | こちら | 理由 |
|---|---|---|---|
| 変換 | 本体のリサンプラに任せる | グルーの中で sinc | blueMSX のミキサーは変換をしない。チャンネルのコールバックは、ミキサーのレートのサンプルを返す決まり（**確認済み(読解)**: `AudioMixer.c` の `mixerSync`） |
| デバイスの数 | FM と SSG で 2 つ（レートが違うので分けるしかない） | ミキサーのチャンネルは 1 つのまま | 変換をグルーが持つので、分ける必要が無い。分けるなら種別の新設（§3.1 で見送り）か、SSG を本体の PSG のスライダーに入れることになる |
| 無音 | バッファを `nullptr` で返して、本体にリサンプルを省かせる | 変換器が積和を省く | 省ける仕事の在りかが違う。こちらのミキサーも `NULL` を返せばそのチャンネルを飛ばすが、省けるのは掛け算 2 回 |
| SSG の 2/3 | デバイスの増幅率にまとめた | サンプルごとに掛ける（`generate()` と同じ式） | チャンネルが 1 つなので、FM との比はグルーの中で決めるしかない。SSG の 3 声の和を 16bit に収める役目もある |

**この表の「デバイスの数」と「SSG の 2/3」の行は `588325e5` の時点のものである。** 2026-10-04 に、
ミキサーのチャンネルは FM と SSG の 2 本になった（§4.7）。

#### 見送ったもの

- **sinc を片側 16 にする** — 見送り。20.8 kHz のレベルが −2.25 → −1.54 dB、SSG 880 Hz の残りが

- **片側 8 にする** — 見送り。SSG 2,976 Hz の残りが 68.8 → 51.4 dB に落ち、17.4 kHz で −0.16 dB、

- **SSG を別のミキサーチャンネルにする** — 見送り。上の表のとおり
  → 2026-10-04 に、利用者の指示で FM と SSG を別々の種別のチャンネルにした（§4.7）。
  変換をグルーの中で持つことと、SSG に 2/3 を掛けることは変えていない
- **ymfm の ADPCM-B の転送を、実機の報告に合わせて直す** — 見送り。ymfm を無改変で持つ決定（§2）を

#### ymfm の挙動で、実機と違うという報告がある点

PR の作者が Makoto の実機で確かめて ymfm を直した点（**伝聞**）。**こちらの ymfm は直していない。**
ADPCM-B の RAM の端を使うソフトが動かなかったら、まずここを見る。

| | こちらの ymfm | 実機の報告（伝聞） |
|---|---|---|
| ADPCM-B の CPU からの書き込み。開始も終了も `0000h`（1bit DRAM）で `A1 A2 A3 A4` を書く | RAM は `A1 A2 A3 FF`。**最後の 1 バイトが書かれない** | 4 バイトとも書かれる |
| ADPCM-B の CPU からの読み出し。RAM に `B1`〜`B8`、limit `0000h` | `B1 B2 B3 B1 B2 B3 B1 B2`。**limit の最後の 1 バイトを読む前に 0 番地へ戻る** | `B1 B2 B3 B4` を繰り返す |
| 終了アドレスまで書かずにモードを切り替えたあとの読み出し | **未確認**（ymfm にはこの挙動が無い、と PR にある） | ADPCM のリセットまで、最後に書いたバイトが返る |

左の列の上 2 行は、使い捨てのプログラムを probe のスタブと組んで走らせて見た（**確認済み** 2026-10-04。
姉妹フォークが同じ版の ymfm で見た結果と同じ）。

ほかに、姉妹フォークが ymfm の挙動として記録している点が 2 つある（どちらも**実機との突き合わせは
されていない**。こちらでは走らせていない）: フラグマスク `110h` のリセット値が `1Ch` で、書き換えるまで
BRDY がステータス 1 に出ないこと。ADPCM-B の EOS と BRDY が、ステータス 1 を読んだときにしか
IRQ に反映されないこと。

読み出しは `B1 B2 B3 B4` の繰り返しになった。**グルーは変えずにビルドでき、probe は 38 項目すべて OK だった。**

**当てて変わるのは、この 2 点だけではない。** PR #40 は EOS と PLAYING を「明示的に消すまで立ったまま」に変え、
再生の終わりの扱いも変える。**ADPCM-B の再生はこちらでは今も確かめていない**（§4.4）ので、当てた版で
再生がどう変わるかは**未確認**である。

**選べる道と値段**（→ 利用者の判断は「今 PR #40 を当てる」。2026-10-04。§4.6）:

| | 何をするか | 値段 |

### 4.6 ymfm に上流の PR #40 を入れる（2026-10-04、`5dcb41a6`）

利用者の指示。上流の `81aec25` に PR #40（head `37d01124`）をマージした結果（衝突なし）から、
`ymfm_adpcm.{h,cpp}` と `ymfm_opn.cpp` の 3 本を置いた。**置いた 3 本はマージ結果の blob と
バイト単位で同じ**（**確認済み**: ハッシュが一致）。ほかの 6 本は `81aec25` のまま。出所は `ymfm/README.md` に書いた。

#### 変わったこと

probe の項目で見た（**確認済み**）。「前」は `588325e5`、「後」は `5dcb41a6`。

| | 前 | 後 |
|---|---|---|
| CPU からの書き込み、開始も終了も `0000h`、`A1 A2 A3 A4` | RAM は `A1 A2 A3 FF` | `A1 A2 A3 A4` |
| CPU からの読み出し、limit `0000h`、RAM は `B1`〜`B8` | `B1 B2 B3 B1 …` | `B1 B2 B3 B4 B1 B2 B3 B4` |
| 再生が終わって立った EOS に、`110h` へ `80h` を書く | 立ったまま | 消える |
| ループ再生の 3 巡目の大きさ（1 巡目との比） | 1.19 倍 | 1.00 倍（ループのたびにデコーダが初期状態から始まる） |
| 再生の音程、ループ無しで終わること、終わりで EOS が立つこと | 合う | 合う |

**後の挙動が実機と合うことは、こちらでは確かめていない。** 根拠は PR の本文とコメント（実機の YM2608 を
測った結果に合わせた、と書かれている）で、**伝聞**である。PR の説明によれば、ブロックの最後の 3 ニブルは
再生されなくなり、PLAYING のフラグとダミーリードの扱いも変わる。これらは probe の項目に無い（§4.4）。

#### ステートの並び

**PR #40 は、ymfm が保存する ADPCM-B のチャンネルの 9 個の値のうち 7 個の意味を変える。大きさは
同じ 36 バイトのまま**なので、大きさでは見分けられない（**確認済み(読解)**: `adpcm_b_channel::save_restore` の差分）。

| 順 | 前 | 後 |
|---|---|---|
| 1 | 状態のビット | 状態のビット（内部用のビットが増えた） |
| 2 | 今のニブルの番号 | 読んだバイトのバッファ |
| 3 | 今のバイト | バッファに在るニブルの数 |
| 4 | ダミーリードの数え | 位置の端数 |
| 5 | 位置の端数 | 今のアドレス |
| 6 | 今のアドレス | アキュムレータ |
| 7 | アキュムレータ | 出力 |
| 8 | 1 つ前のアキュムレータ | 1 つ前の出力 |
| 9 | ステップ幅 | ステップ幅 |

**前の版が書いたステートをそのまま読むとどうなるか**（**確認済み**）: FM は戻る。ADPCM-B は無音になる
（読み替えた状態に「再生中」の内部ビットが立たないため）が、**出力に直流が残る**（試験の条件で −3966）。
アドレスは位置の端数から取られる（こちらは読解で、動かして見てはいない）。

**対処**: ステートに、ymfm の状態の並びを示す番号 `chipStateLayout` を書く（今は 2。項目が無ければ 1）。
読んだ番号が今と違えば、ymfm の状態を戻したあとで **ADPCM-B のチャンネルを初期状態にする。レジスタは残す。**
再生中だった ADPCM-B はロードの後で止まり、ほかはそのまま続く。開始の命令をもう一度書けば、保存の前に
設定したアドレス・速さ・音量で再生が始まる（**確認済み**）。

**確かめ方**: 同じプロセスの中では古い並びのステートを作れないので、probe に「ステートをファイルに書く / 読む」
モードを足し、**`588325e5` で組んだ probe が書いたステートを、`5dcb41a6` で組んだ probe に読ませた**（§4.2）。

**前提**: ymfm が保存する中身を変える更新を入れるたびに、番号を上げて古い番号の扱いを書く。
**大きさが同じだと黙って通る**ので、ymfm を上げるときは `save_restore` の差分を読むこと
（`ymfm/README.md` にも書いた）。**番号の名前と値は外に出る値で、利用者には事後の報告になった。**

見送ったもの: **古い並びの 9 個の値を新しい並びに読み替える**案。2 つの版は状態の持ち方そのものが違い
（ダミーリードの数え方、内部の状態ビット）、読み替えが合っていることを確かめる試験が、再生中・読み出し中・
書き込み中のそれぞれに要る。公開済みなのは pre-release の 2 本で、ADPCM-B の途中で保存したステートに限った話なので、
止めて始め直す形にした。

#### 負荷

PR #40 を入れると、音 1 秒ぶんのホスト時間が無音で約 1.2 ms、演奏中で約 1.7 ms 増えた（**確認済み**:
同じ回に 5 巡。最小 / 中央は、前が 16.46 / 16.61 ms と 32.37 / 32.85 ms、後が 17.66 / 17.86 ms と
34.08 / 34.34 ms。§4.5 の表とは別の回で、機械の状態が違うので直接は比べない）。ADPCM-B を鳴らして
いなくても増える。上流の作りによるもので、手は入れていない。

### 4.7 FM と SSG の音量を別々にする（2026-10-04、`f7a4d0f8`）

利用者の指摘: FM と SSG のゲインを別々に調整できないと不便。実機でも、2 つの出力の比は基板の
ミキサー回路で決まる。

#### 選んだ形（ユーザー判断。決める前に、値段を付けて聞いた）

| 案 | 中身 | 結果 |
|---|---|---|
| SSG だけ専用の種別 | FM は SFG のスライダーのまま、SSG を新しい種別に | 見送り |
| **FM も SSG も専用の種別** | SFG から切り離す。どちらも `bluemsx.ini` で調整 | **採用** |
| SSG を本体の PSG の種別に入れる | 画面から調整できるが、本体の PSG と連動する | 見送り。Y8960 のときに却下した形 |
| ミキサー画面にスライダーも足す | 約 10 ファイルに波及 | 見送り |

種別の名前は `MIXER_CHANNEL_OPNA_FM` と `MIXER_CHANNEL_OPNA_SSG`（ユーザー判断。§3.4）。

#### 作り

- `AudioMixer.h` の種別に 2 つ足した。位置は `MIXER_CHANNEL_CASSETTE` の後、`MIXER_CHANNEL_TYPE_COUNT` の前
  （同ファイルの注記のとおり、`MIXER_CHANNEL_MIDI` より前には挿さない）
- `Properties.c` に既定値（有効・パン 50・音量 95。SFG の既定と同じ）と、設定ファイルの読み書きを足した
- `YM2608.cpp` は、FM+リズム+ADPCM をステレオのチャンネル、SSG をモノラルのチャンネルとして別々に登録する。
  レートの通知は FM のチャンネルの分だけを受けて、両方のレートを取り直す
- **ミキサー画面には出ない**（Y8960 の種別と同じ。§4.4）

**既定では、分ける前と同じ音になる。** ミキサーは種別の音量とパンから左右の係数を作り、モノラルの
チャンネルにはその係数を左右それぞれに掛ける（**確認済み(読解)**: `AudioMixer.c` の
`recalculateChannelVolume` と `mixerSync`）。録音でも、6 区間の大きさは分ける前と同じだった（§4.2）。

試験 ROM を走らせ、区間ごとの大きさ（録音の実効値）を見た。

### 4.8 SSG を本体の `AY8910.c` に置き換えるか（2026-10-04、置き換えない）

利用者の問い: openMSX は SSG の部分を差し替える方向だが、こちらではどう判断するか。

**openMSX の現状**（2026-10-04 に見た）: PR #2209 のレビュー担当が、SSG を openMSX の既存の `AY8910` に
置き換える案を出し、クロックを引数にする一般化を自分で進めると書いている。**PR の head（`e34f671e6`）にも
upstream の master にも、まだ入っていない。**

**判断: 置き換えない。** 差し替え先の中身が違う。

| | openMSX の `AY8910` | blueMSX の `AY8910.c` |
|---|---|---|

| クロックとレート | クロックは固定で、引数にする一般化が進行中 | **3.579545 MHz 系のクロックと 44.1 kHz が、1 つの定数（`BASE_PHASE_STEP`）に埋め込まれている**。レートの通知も受けない |
| 変換 | 本体のリサンプラが帯域を制限する | 上の平均とフィルタだけ |
| ミキサーの種別 | — | `MIXER_CHANNEL_PSG` に固定 |

同じ測り方（§4.5 の「残り」）で比べた（**確認済み**。`AY8910.c` だけを組んだ使い捨てのプログラムで測った）。

| | 今の Makoto の SSG | 本体の `AY8910.c` |
|---|---|---|
| 440 Hz: レベル / 残り | 0.00 dB / 41.4 dB | 0.00 dB / 35.8 dB |
| 約 3 kHz | +0.00 / 68.8 | −0.58 / 27.7 |
| 約 6 kHz | +0.01 / 67.5 | −2.00 / 23.7 |
| 約 10 kHz | +0.02 / 65.9 | **−4.41 / 17.5** |
| 約 16 kHz | +0.06 / 63.1 | −7.35 / 21.3 |
| 負荷（音 1 秒ぶんのホスト時間） | 無音で約 7.7 ms、演奏中で約 9.5 ms（下） | 約 2.9 ms（無音でも演奏中でも同じ） |

**今の SSG の負荷の内訳**（**確認済み**: グルーから SSG を抜いた版・変換だけ抜いた版と、同じ回に 5 巡して比べた）:
SSG を丸ごと抜くと、無音で 17.8 → 10.0 ms、演奏中で 33.7 → 24.2 ms（中央）。変換だけを抜くと、

計算する形に作り直したら、判断し直す。

（負荷を減らし、音は保つ）を得るにはこれが要るが、差し替えではなく新規の実装になる。見積もっていない。

### 4.9 Z80 を速くした機種構成が、起動ロゴから進まない（2026-10-04 に調べた）

**Makoto とは関係が無い。** デプロイ先にある、利用者が手を入れた機種構成（Z80 の周波数を標準の 3 倍にしたもの）で
試験 ROM の録音が無音になったので、利用者の指示で調べた。

| 見たこと | 結果 |
|---|---|
| 機種構成が指す ROM の実在、`/listmachines` に出るか | すべて実在し、一覧にも出る |
| `bootmark.rom`（本体の PSG だけ）を、その機種で Makoto 無し / 有りで走らせる | **どちらも無音** |
| 同じ ROM を C-BIOS 機、手を入れていない `HB-F1XDJ`・`HB-F1XV` で | 鳴る（999 Hz → 1998 Hz） |
| その構成の設定を 1 つずつ標準に戻した写し（Z80 の周波数、VRAM、RAM、ディスク ROM の位置、スロット 3-3 の ROM） | **Z80 の周波数を 3.58 MHz に戻した写しだけが鳴る** |
| 手を入れていない `HB-F1XV` の Z80 の周波数だけを変える | 3.58 MHz と 5.37 MHz（1.5 倍）は鳴る。**7.16 MHz（2 倍）と 10.74 MHz（3 倍）は無音** |
| 無音の構成を 70 秒録る | 70 秒とも無音（遅いのではない） |
| エミュレータ自身のスクリーンショット（起動 15 秒後） | **MSX2+ の起動ロゴのまま止まっている。** ロゴの下に崩れた描画の断片がある。3.58 MHz ではロゴを抜けている |
| 設定の「VDP command wait」（`emulation.vdpCmdSpeed`、既定 100）を変える | 7.16 MHz は 50 と 0 で起動。10.74 MHz と、利用者の構成そのものは 0 で起動 |

いずれも **確認済み**（デプロイ先の exe、`/hidden`。写しは一時フォルダに作り、`/machinedir` で読ませた。
利用者のインストールは書き換えていない）。

**原因**: VDP のコマンドの待ち時間の再現（既定 100%）と、2 倍以上に速くした Z80 の組み合わせ。
実機の BIOS のロゴの描画が、VDP のコマンドの終わりを待たずに先へ進み、そのまま戻ってこない。
**どの命令で止まっているかまでは見ていない**（決めるには、ロゴの描画の間の VDP への書き込みを記録する）。

**上流はこの夏に VDP のコマンドの時間を大きく作り直している**（`9323b725` から `38000593`、2026-08-23〜26）。
**その前の版でこの構成が起動したかは未確認**（決めるには、`9323b725` の手前を組んで同じ試験を掛ける。
ただしその版は `/hidden` を持たない）。利用者の通常のインストールの exe でも試していない（ウィンドウが出るため）。

**今できる回避**: Z80 を速くした機種を使うときは、設定の「VDP command wait」を下げる
（2 倍なら 50 以下、3 倍なら 0 で起動した。間の値は試していない）。

**これは上流の挙動であって、このフォークの変更で起きたことではない**（`feature/makoto-opna` は
`upstream/develop` に Makoto を足しただけで、VDP と Z80 には触れていない。**確認済み**:
`git diff --stat upstream/develop...feature/makoto-opna` に `VideoChips/` と `Z80/` が無い）。

**利用者が後で上流に issue を出す**（2026-10-04 ユーザー判断）。`doc/fork/README.md` の「これから出すもの」にも載せた。
