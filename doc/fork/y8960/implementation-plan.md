## 確度の読み方

本書の記述には確度を付ける。

- **確認済み** — 走らせて確かめた。何でどう確かめたかを添える
- **確認済み(読解)** — 当該ファイルを読んで確認した。ファイル名と行を示す
- **未検証** — 読解して組み立てた設計だが、動かして確かめていない

## 1. 目的とスコープ

Y8960 カートリッジ（hra1129/Y8960_Cartridge）を blueMSX+ でエミュレートする。

**Y8960 を構成するデバイスブロックは、個別にマシン構成へ追加できるようにする**
（2026-09-12 ユーザー指示）。カートリッジ一体ではなく、ブロックごとに独立した
`RomType` を持たせ、`Machines/<名前>/config.ini` の `[Slots]` 行に 1 行ずつ
書けるようにする。理由は Y8960 のハードウェアがまだ WIP であり、
**どのブロックが最終的にどう組み合わさるかが決まっていない**こと。

対象ブロックは 7 つ。

| ブロック | 相当チップ | 備考 |
|---|---|---|
| OPLLEX | YM2413 + チャンネル別音色バンク | 2 回路 |
| OPL2EX | YM3812 + ADPCM-B | 2 回路。レジスタ配置は Y8950 と同一 |
| SSGS | YMZ705/732 相当 | 内部に YM2149 相当が 2 系統、チャンネルごとパンポット |
| MSX-TIMER | 独自 | 4 本のカウンタ + 割り込み |
| MSX-MIXER | 独自 | ブロックごとの左右ゲイン |
| Y8960 SCC | Konami SCC + 独自マッパー | バンクメモリを含む |
| DCSG | SN76489 | 2 回路。**音源コアは blueMSX に既存** |

### スコープ外

- FPGA コンフィグ・SPI Flash・SRAM 初期化シーケンス。実機の起動手順であって、
  エミュレータでは初期化済みで持てばよい
- ADPCM メモリの構成切り替え（**実機側で設定方法が未実装**）。
  ただし**器は 4 状態ぶん作る**。実装するのは起動時の共有モードだけ（§5.1）
- BIOS ROM イメージ（存在しない）

#### 決着が付いたもの

**訂正**: 本書は当初、MSSX の文を「RAM モード 0 のとき**または** BANK1 に ROM」
という 2 条件の or と読み、RAM モード 0 で BANK1 が SCC のときに食い違うと

## 4. blueMSX+ の作法（調査結果）

すべて **確認済み(読解)**。2026-09-12 に当該ファイルを読んだ。

### 4.1 デバイスの足し方

blueMSX のデバイスは `RomType`（`Src/Media/MediaDb.h` の enum、現在
`ROM_MAXROMID = 179`）で識別される。1 ブロックを足すのに触るのは次の 6 か所。

| 場所 | 何を足すか |
|---|---|
| `Src/Media/MediaDb.h` | enum の値。`ROM_MAXROMID` も更新 |
| `Src/Media/MediaDb.cpp` | `mediaDbStringToType`（DB の XML 名 → enum）、`romTypeToString`（表示名）、`romTypeToShortString`（短縮名） |
| `Src/Board/Machine.c` | 生成。ROM を伴わないデバイスは前半のループ、伴うものは後半の `switch` |
| `Src/Memory/romMapper<名前>.c` | 実装本体 |
| `Src/Win32/Win32machineConfig.c` | マシン構成エディタの一覧と、ROM ファイルを要求するかどうかの分岐 |
| `Src/Language/` | `romTypeToString` が返す表示名の文字列 |

**`config.ini` に書かれるのは enum の数値**である（**確認済み(読解)**:
`Machines/*/config.ini` の `[Slots]` 行は
`スロット サブスロット 開始ページ ページ数 romType "ROMファイル" ""` の形）。
したがって数値を後から変えると、既に作ったマシン構成ファイルが全部ずれる。

**ROM を伴わないデバイスの最小形**は `Src/Memory/romMapperTurboRTimer.c`（135 行）が
そのまま雛形になる。`deviceManagerRegister(romType, &callbacks, ref)` で
destroy / reset / saveState / loadState を登録し、`ioPortRegister` でポートを取る。

### 4.2 I/O ポートの重ね合わせ — **上流を直した（2026-09-12）**

**直す前の状態**（**確認済み(読解)**）。`ioPortRegister` は 1 ポートに 1 デバイス
しか登録できず、**既に誰かが登録していると黙って無視していた**。
戻り値が無いので呼び出し側は気づけない。

Y8960 は**設計上、本体デバイスと同じポートに重なる**ブロックを持つ。

| ポート | Y8960 | 本体側 | 重なりの意図 |
|---|---|---|---|
| A0h-A2h | SSGS | PSG | **設計どおり**。カートリッジ版 SSGS は本体 PSG に重ねて発音するだけの存在で、読み出しは本体 PSG が担う（`hardware-notes.md` §2） |
| 7Ch-7Dh | OPLL #1 | MSX-MUSIC | 機種による |
| C0h-C3h | OPL2 #1/#2 | MSX-AUDIO | 機種による |

しかも `Src/Board/MSX.c:253-259` は **`machineInitialize()` でスロットのデバイスを
作ってから `msxPsgCreate()` を呼ぶ**ので、マシン構成に置いた Y8960 SSGS は
本体 PSG より先に登録され、**本体 PSG の A0h / A1h 登録が黙って落ちていた**はずだった。

**2026-09-12 のユーザー判断により、これをエミュレータの不具合として上流を直した。**
実機のバスでは複数のデバイスが同じポートに応答しうる。

#### 直した内容

`Src/Memory/IoPort.c` と `IoPort.h`。

| | |
|---|---|
| 登録 | 1 ポートあたり **`IO_PORT_MAX_CLAIMS` (= 4) 件**まで持てる。同じ `ref` の再登録は上書き |

### 4.3 サウンドの出し方

`mixerRegisterChannel(mixer, audioType, stereo, updateCb, rateCb, ref)` で登録する

したがって **MSX-MIXER のゲインは、各ブロックが自分の出力に自分で掛ける**形になる。
§5.6 に設計を書く。

## 5. ブロックごとの実装方針

### 5.1 OPL2EX（YM3812 + ADPCM-B）×2【実装済み 2026-09-12】

**土台は `Src/SoundChips/OpenMsxY8950Latest/` の移植版のフォーク。**
フォーク先は `Src/SoundChips/Y8960Opl2Core.*` と `Y8960Opl2Adpcm.*`。

blueMSX+ は openMSX の最新 Y8950 を既に移植して持っている
（**確認済み(読解)**: `OpenMsxY8950Latest.h` の冒頭）。
**openMSX_Y8960 の `Y8960OPL2` も同じ openMSX `Y8950` のフォーク**なので、
当てる差分は向こうと同じになる。

**namespace を `openmsx` から `y8960opl2` に変えてある。**
本体の MSX-AUDIO が素の移植版を使うので、**同じバイナリに両方が入る**。
OPLLEX でシンボルを改名したのと同じ理由で、C++ では namespace で足りる。

当てた差分は 3 つ。

| | 内容 |
|---|---|
| **波形選択** | `sinTable` から 4 面のテーブルを作り、スロットが `wave` を持つ。`E0h`-`F5h` がスロットごとに選び、`01h` の b5 が全体のゲート。**リズム用スロットはサインのまま** |
| **落とした部分** | キーボードコネクタ（`05h` 読み / `06h` 書き）、13bit DAC（`15h`-`17h`）、`Y8950Periphery`（`18h` / `19h`、`07h` の b3 の SP-OFF） |
| **ADPCM** | サンプル RAM を回路の外に出し、2 回路で共有する |

#### `15h`-`17h` は落とすのではなく ADPCM に回す

**写しの §5.1 は「落とすレジスタ」に `15h`-`17h` を挙げていたが、これは誤り**
だった。仕様シート `OPL2+ADPCM` は **`07h`, `09h`-`12h`, `15h`-`17h` を
ADPCM-B のレジスタ**と書いている（**確認済み(読解)**: madscient/Y8960emu の
`src/opl2ex.h` 冒頭。同じ表が本書 §5.1 の冒頭にも写してあった）。

**Y8950 だけが `15h`-`17h` を 13bit DAC に使っている。** ADPCM-B 本来の
番号では limit / DAC 出力 / ROM フラグに当たる。
**移植元の ADPCM はこれらを受け取って何もしない**（**確認済み(読解)**:
`Y8960Opl2Adpcm.cpp` の `writeReg` の最後の `case`）ので、
**DAC へ回すのをやめて ADPCM へ回すだけで済んだ。**

`0Dh` / `0Eh` / `1Ah` も同じく ADPCM が受けて無視する。

#### `08h` の bit 0 は何も選ばない

**Y8960 の ADPCM にサンプル ROM は無い**（2026-09-12 ユーザー回答。
openMSX_Y8960 の `hardware-notes.md` §6 に記載）。Y8950 はこのビットで ADPCM を
ROM 側へ切り替え、書き込みを捨てて読みを 0 にするが、**Y8960 の後ろには SRAM しか無い。**
移植元はこれを残していたので落とした（§11 の (21)）。
bit 1 の 64K モードについては情報が無く、移植元のまま。

#### サンプル RAM は 4 状態をとる

**2026-09-12 にユーザーから直接の回答があった**（最も強い出典）。

256KB を 2 回路でどう分けるかに **4 つの状態がある**。

| 状態 | |
|---|---|
| **共有** | 2 回路が同じ 256KB を見る |
| **片寄せ（回路 1）** | 256KB を回路 1 に割り当てる |
| **片寄せ（回路 2）** | 256KB を回路 2 に割り当てる |
| **分割** | 128KB + 128KB |

**設定の方法は実機側で未実装である。** 起動時は共有モードという前提を置く
（ユーザーの暫定判断）。**MSSX も共有モードで動く前提**である。

**器は 4 状態ぶん作った。** `Y8960Opl2Core.h` の `SampleRam` が RAM 本体を
持ち、**回路はモードが決めた窓だけを、0 番地から見る**。
移植元の `TrackedRam` は回路ごとに RAM を抱えていたので、そこを置き換えた。
**切り替えレジスタが決まったら、足すのは `setMode` を呼ぶ口だけで済む。**

**窓の外へは書けない。** 片寄せで窓を持たない側は `span` が 0 になり、
書き込みが 1 バイトも入らない（**確認済み**: §8.1 の probe）。

**openMSX_Y8960 とは違う。** あちらは `<sampleram>256` をブロックごとに
持たせており、2 回路が別々の 256KB を見る（どの状態にも当たらない）。

**クロックは 3.579545MHz**（§3.3）。

#### 割り込み線は回路ごとに別のビット

移植元の `IRQHelper` は MSX-AUDIO のビット `0x10` を直に叩いていた。
**カートリッジの 2 回路と本体の MSX-AUDIO が同時に在りうる**ので、
**マスクを回路ごとに与える形に変えた**（回路 1 が `0x2000`、回路 2 が `0x4000`）。
片方が他方の pending を落とすと割り込みが消える。
MSX-TIMER が `0x1000` を取ったのと同じ選び方である（`romMapperY8960Timer.c`）。

#### I/O とトンネル

| | |
|---|---|
| 直接 I/O | 回路 1 が `C0h`（アドレス）/ `C1h`（データ）、回路 2 が `C2h` / `C3h`。**読み書きとも** |
| イネーブラ | `Y8960_IO_OPL20` / `Y8960_IO_OPL21`（§5.8）。閉じているとき読み出しは `FFh` |
| トンネル | `7FEEh`/`7FEFh` が回路 1、`7FECh`/`7FEDh` が回路 2。**ゲートしない** |

**バックエンド切替の対象にはしない。** blueMSX+ の Y8950 は
`Y8950BackendBase` の下に複数実装を並べてユーザーが切り替えられる作りだが、
Y8960 の OPL2 は 2 回路あり、切替の器を 2 つ持つ意味が薄い。
**独立したデバイスとして作った。** OPLLEX を emu2413 1 本に決めた判断（§5.2）と揃えた。

**前提**: この判断は「Y8960 が WIP で、音質の比較検討より先に動くことが要る」
段階であることに依っている。仕様が固まって A/B 比較が要るようになったら見直す。
**やり直しの値段**: `Y8950BackendBase` を継承する形に変え、
`Y8950MultiBackend` に相当する器を Y8960 用に 1 本作る。デバイス側は変わらない。

#### 確かめたこと

**コア単体**（`tests/opl2ex-probe.cpp`、14 項目）で確認した。§11 の (14)。
**エミュレータの中でも確認した**（`banktest.asm` の 10 と 11）。§11 の (17)。

**このブロックは読み戻せるので、ゲートもトンネルも 2 回路の独立も
音を聴かずに判定できる。** 読み出しを持たない OPLL / DCSG との違い。

### 5.2 OPLLEX（チャンネル別音色バンク付き YM2413）×2【実装済み 2026-09-12】

**土台は `Src/SoundChips/Emu2413/` のフォーク**（2026-09-12 ユーザー決定）。
フォーク先は `Src/SoundChips/Y8960OpllCore.c` / `.h`。

**公開シンボルは `OPLL_*` → `Y8960OPLL_*` に機械的に改名してある。**
本体の MSX-MUSIC が素の emu2413 を使うので、**同じバイナリに両方が入る**。
改名しないとリンクが通らない。

| | 内容 |
|---|---|
| 音色テーブルを 4 面持つ | `patch[19*2]` を `patch[4][19*2]` に広げた |
| チャンネルごとにバンクを選ぶ | `set_patch()` が `patch_bank[ch]` を見て向け先を選ぶ |
| バンクレジスタ | `40h`-`48h`（ch0-ch8）の b1:b0。`reg[]` を `0x40` から `0x49` 語へ広げた |

#### 決めたこと

| | 決定 | 理由 |
|---|---|---|
| **音色データの出所** | **4 バンクとも "Copyright free OPLL(x) ROM patches"（David Viens / Hubert Lamontagne、CC BY-SA）** | 2026-09-12 ユーザー判断。NukedOPLL の表は decap 由来でライセンス上の懸念がある。§9.2 |
| データの取り込み経路 | madscient/Y8960emu の `src/opllex.cpp` から機械的に写した | 同じ出典・同じ 8 バイト形式で、同じ帰属表示が付いている |
| リズム 3 音色 | 4 バンク共通 | 一次情報に記載が無い。ymfm が同じ出典として持っているものを Y8960emu 経由で採った。**実機のリズム ROM がバンクごとに違うかは未確認** |
| **ユーザー音色（音色 0）** | **バンクに属さない。チップに 1 つ持つ** | レジスタ `00h`-`07h` はチップに 1 組しかない。バンクを変えてもユーザー音色は変わらない（**確認済み**: §8.1 の probe） |
| 出力の倍率 | `Emu2413Backend` と同じ `× 32767*9/10 ÷ 1024` | 本体 MSX-MUSIC と同じ高さに置く。この係数だけが**測って決められた**もの（emu2413 を OpenYM2413_2 に RMS 合わせした値）。他の Y8960 ブロックとの釣り合いは**未検証** |
| アナログ後段フィルタ | **持たない** | 本体 MSX-MUSIC のフィルタは向こうの設定項目であり、カートリッジのアナログ段は文書化されていない |
| セーブステート | **レジスタを保存し、読み込みで書き直す** | レジスタがプログラムされた状態のすべてである。失うのは包絡線と位相の進み具合で、読み込み点で 1 回音が途切れる |

**バンク 0 の音は本体 MSX-MUSIC と完全には一致しない。** 出所を 4 バンクで
揃えた結果で、意図した差である（plgDavid 表と Okazaki 表は AR/DR などが違う）。

#### 確かめたこと

**コア単体**（`tests/opllex-bank-probe.c`、13 項目）と、**エミュレータを起動しての
聴取**（`banktest.asm` の 9、A-E）の両方で確認した。詳細は §11 の (12) と (13)。

#### I/O とトンネル

| | |
|---|---|
| 直接 I/O | 回路 0 が `7Ch`（アドレス）/ `7Dh`（データ）、回路 1 が `7Ah` / `7Bh`。**ライトオンリー** |
| イネーブラ | `Y8960_IO_OPLL0` / `Y8960_IO_OPLL1`（§5.8） |
| トンネル | `7FF4h`/`7FF5h` が回路 0、`7FF2h`/`7FF3h` が回路 1。**ゲートしない** |

**回路 0 を `7Ch`-`7Dh` に置いたのは FM-PAC を正とする読みによる**（§3.3 の #5）。

### 5.3 SSGS（YMZ705/732 相当）×1【実装済み 2026-09-12】

**土台は `Src/SoundChips/AY8910.c` のフォーク。** フォーク先は `Y8960Ssgs.c` / `.h`。

| | 内容 |
|---|---|
| レジスタ配置 | `$00-$1F` が SSG-1、`$20-$3F` が SSG-2。系統の選択は `(reg >> 5) & 1`。各系統内は `sub = reg & 0x1F` |
| `$0E-$0F` | **無い**。YMZ 系は I/O ポートを持たない。ただし **SSG-2 の `$0F`（= `2Fh`）は LED** |
| `$10-$12` | ch A/B/C の 4bit パンポット |
| `$13-$1F` | 未定義。無視する |
| `$40` 以上 | YMZ の ADPCM / シーケンサ領域。**このブロックは持たない**ので無視する |
| 出力 | 1 つのステレオ・サウンドデバイス（6ch）。`mixerRegisterChannel(..., stereo=1, ...)` |

**クロックは 1.7897725MHz**（`3.579545 / 2`。§3.3）。**本体 PSG と同じなので、
`BASE_PHASE_STEP` はそのまま使える**（**確認済み(読解)**: `AY8910.c` の同定数が
`3579545 / 32` で組まれており、これは `1789772.5 / 16` に等しい）。

**エンベロープは YM2149 の 32 段**にした。コアが YM2149 相当であるため。

#### パンポットの分配則は左右非対称である

EPSGemuEngine（`src/YmzSsg.cpp` の `pan_gain`）と openMSX_Y8960 が採る
YMZ280B と同じ則に合わせた。**データシートに記載は無く、実装者の判断である。**

```
中央(8)      : 左右とも全開
中央より下   : 左 全開、右 = (pan - 1) / 7   （pan 0 は 0）
中央より上   : 右 全開、左 = (15 - pan) / 7
```

**左端は 2 段（0 と 1）が全振り、右端は 1 段（15）だけである**
（**確認済み**: §8.1 の probe で測った）。
`hardware-notes.md` の写しは「端の 2 段は片側全振り」と書いているが、
**これは左端についてのみ正しい。** 式から出る非対称であって、
移植元がそう書いてある。

#### パンポットの挙動は暫定である

**ハードウェアの仕様が固まるまでの暫定実装でよい**（2026-09-12 ユーザー指示）。
分配則もリセット値も、**データシートにも RTL にも無い。**

**リセット後は中央（8）にする**（2026-09-12 ユーザー判断）。
一度 0 と決めたが、**`MSX2++` では SSGS が本体の PSG そのものになる**ため、
0（＝この則では左端）だと**パンを触らない既存の PSG 曲が全部左からしか
鳴らない**。その帰結は内蔵版の話が出るまで見えていなかった（§11 の (16)）。

**もう一つの候補: `0` と `8` をともに中央とする方式**（2026-09-12 ユーザー）。
いまの則は左が 0-7 の 8 段、右が 9-15 の 7 段で**左右の分解能が揃っていない**
（そのため 0 と 1 がどちらも左端になる）。0 を中央に寄せれば
1-7 と 9-15 で 7 段ずつになり揃う。**採否はハードウェア仕様が決まってから。**

**やり直しの値段**: 則を変えるなら `buildPanTable` 1 つと、probe の期待値。

#### 直流の扱いは土台が既に済ませていた

写しは「AY コアの出力は片極性なので、パンを掛ける前に無音時レベルを差し引く」
と書いている。**blueMSX の `AY8910.c` は音量テーブルを組んだ直後に
`voltTable[i] -= voltTable[0]` を実行しており、無音時レベルは既に 0 である**
（**確認済み(読解)**: `AY8910.c:265-270`）。

**したがって追加の補正は要らない。** 引き算を落とすとどうなるかは
probe で確かめてある（落とした版は 5 項目で落ちる。§11 の (15)）。
波形自体の直流は、土台が持つ 1 次ハイパスが従来どおり除去する。

#### リセットはフィルタの履歴も消す

`AY8910.c` の `ay8910Reset` は**レジスタに 0 を書くだけ**で、
直流除去とローパスの状態を残す。**時定数が長い**ので、
リセット直後にも前の音が数千サンプル漏れ出す。
**フォーク側では消すようにした**（**確認済み**: 消す前は probe が 8 項目で落ちた）。

#### カートリッジのときと本体内蔵のときで違う

**2026-09-12 のユーザー指示。**

| | カートリッジ | 本体内蔵 |
|---|---|---|
| 読み出し | **持たない。** 本体 PSG が `A2h` を駆動する | **持つ** |
| 立場 | 本体 PSG に重ねて発音するだけ | **標準の PSG の代わりになる** |
| GPIO（`0Eh` / `0Fh`） | **無い** | **本体 PSG と同じものが繋がる**（ジョイスティック、カセット、かな LED） |

**チップ側の器は両方ぶん作った**（`Y8960Ssgs.c`）。

| | |
|---|---|
| `y8960SsgsReadData` | 選択中のレジスタを返す。**持たないレジスタは `FFh`** — 重ね合わせでは AND なので、`FFh` が「駆動していない」を意味する（§4.2）。**4bit のレジスタ（パンポットと LED）は上位を 0 にして返す**（openMSX_Y8960 に揃えた。§11 の (22)） |
| `y8960SsgsSetIoPort` | `ay8910SetIoPort` と同じ形。**繋がっているときだけ SSG-1 の `0Eh` / `0Fh` が生きる** |

**写しの `$0E-$0F` は「無い（カートリッジ版の場合）」と書いてあった。**
その括弧書きが指していたのがこの違いである。

**本体内蔵版は `MSX2++` という機種として出す**（§9.9 で決着）。
`MsxPsg` が AY8910 の代わりにこのチップを持ち、`A0h`/`A1h` 書き・`A2h` 読みを
登録し、**自分が持っている GPIO の配線をそのまま渡す**。
スロットには置かない。カートリッジ空間のデバイスではないため。

#### I/O とトンネル（カートリッジ版）

| | |
|---|---|
| 直接 I/O | `A0h`（アドレス）/ `A1h`（データ）。**ライトオンリー** |
| `A2h` | **登録しない。** 読み出しは本体 PSG だけが駆動する |
| イネーブラ | `Y8960_IO_SSGS`（§5.8） |
| トンネル | `7FEAh`（レジスタ）/ `7FEBh`（値）。**ゲートしない** |

**A0h / A1h が本体 PSG と重なる件は、上流を直して解決してある**（§4.2）。

#### 確かめたこと

**コア単体**（`tests/ssgs-probe.c`、16 項目）で確認した。§11 の (15)。
**エミュレータの中でも確認した** — 内蔵版は §11 の (16)、

### 5.4 DCSG（SN76489）×2

**音源コアは `Src/SoundChips/SN76489.c` をフォークした
`Src/SoundChips/Y8960Dcsg.c`。** カートリッジ内の回路は TI SN76489 そのもの
ではなく等価回路なので、本体のコアを共有せず別のチップとして持つ（§11 2026-09-12 (10)）。
2 インスタンスを作り、3Eh → DCSG 0、3Fh → DCSG 1 に載せる
（アドレス bit0 が回路を選ぶ。`hardware-notes.md` §7.1）。
1 バイト書き込みのみのレジスタラッチ方式なのでライトオンリー。

openMSX 側が `SNPSG` に足さず別デバイスに切り出した理由（イネーブラのゲートと
トンネルの入口が要り、既定値が他デバイスと逆になる）は blueMSX+ でも同じなので、
**`Src/Memory/romMapperY8960Dcsg.c` を別に作り、フォークしたコアを呼ぶだけにする。**

**実装済み（Phase 2-1）。** 以下は着手前の見立てで、そのとおりになった。

**上流の `sn76489Create(Mixer*)` はそのままでは使えない。**
ミキサー種別が `MIXER_CHANNEL_PSG` に、デバッガの表示名が `"SN76489 PSG"` に
固定されている（**確認済み(読解)**: `SN76489.c:226-227`。
同ファイル 485 行にもう一つ `sn76489Create` があるが、42 行目の `#if 1` /
376 行目の `#else` に挟まれた**死んだ側**である）。

Y8960 の DCSG は専用のミキサー種別（§6）に載せ、2 回路を区別できる名前が要るので、
**フォークした側で種別を固定し、名前を引数に取る形にする。**

#### 実装（Phase 2-1、2026-09-12）

`Src/Memory/romMapperY8960Dcsg.c` と、コアの `Src/SoundChips/Y8960Dcsg.{c,h}`。

**コアは `SN76489.{c,h}` の写しで、公開シンボルだけ改名してある**
（`SN76489` → `Y8960DcsgChip`、`sn76489Xxx` → `y8960DcsgXxx`）。
内部の変数名は上流のまま残してあるので、上流が直したときに差分を取れる。
上の**死んだ側 274 行は落とした**。
`y8960DcsgCreate(mixer, name)` は `MIXER_CHANNEL_Y8960` に固定で載せ、
2 回路を `"Y8960 DCSG 0"` / `"Y8960 DCSG 1"` として区別する。

**セーブステートの節名は `y8960dcsg` に変えてある。** `saveStateOpenForWrite` は
同じ名前を `_00` `_01` と連番で割り振るので（**確認済み(読解)**:
`Utils/SaveState.c` の `getIndexedFilename`）、本体の SN76489 と名前を共有すると
両者の状態がデバイスの生成順だけで区別されることになる。別のチップなので分ける。

**直接 I/O は書き込み専用で登録する。** DCSG には読み出すものが無く、
`3Eh` / `3Fh` は本体の何かと重なりうる。

#### 確かめたこと（**確認済み** 2026-09-12）

テスト ROM の `t8:` が、イネーブラの状態を変えながら別々の値を書く。
書き込み口に記録を入れて読んだ結果が次。**出なかった行にも意味がある。**

| 書いた先 | 値 | イネーブラ | 届いたか |
|---|---|---|---|
| `3Eh` | 11h | DCSG0 閉 | **届かない** |
| `3Eh` | 22h | DCSG0 開 | 届いた（ch0） |
| `3Fh` | 33h | DCSG1 **閉**（DCSG0 だけ開けた） | **届かない** |
| `7FF1h` | 44h | — | 届いた（ch0） |
| `7FF0h` | 55h | — | 届いた（ch1） |

**1 回の掃き出しで 5 つ確かめられている。** ゲートが効くこと、開くと届くこと、
**2 回路が別々にゲートされること**、トンネルがゲートを受けないこと、
そしてトンネルの宛先が窓の並び（高位が 1 番目）どおりであること。

記録はコミットしていない。掃き出しはテスト ROM に残してある。

**音とゲートは `sndtest` で確かめた**（**確認済み** 2026-09-13、§11 の (24)）。
録音を `analyze-sndtest.py` が読み、鳴るべき 3 ステップの音程だけが並ぶことを見る。
ユーザーも同じ実行を聴いて、DCSG が鳴っていることを確かめた。
**2 回路の取り違えはこの方法では分からない**（§0）。

### 5.5 MSX-TIMER

**新規実装。** 移植元は openMSX_Y8960 の `src/sound/MSXTimer.cc`（517 行）。

| | 内容 |
|---|---|
| ポート | B0h = レジスタ番号、B1h = 値、B2h = 割り込みフラグ、B3h = カウンタ読み出し |
| 分解能 | Base Clock 85.909080MHz (= 3579545 × 24) を `2^(10+2r)` で分周。8 段 |
| 割り込み | `boardSetInt` / `boardClearInt`（**確認済み(読解)**: `Src/Board/Board.h:151-152`） |
| 時間の進め方 | `boardTimerCreate` / `boardTimerAdd`（同 211-213 行） |

**openMSX 側で踏んだ落とし穴を引き継ぐ**: カウント計算が 32bit を溢れると、
分解能 7・終端値 255 でカウンタが張り付く（openMSX_Y8960 の経緯 2026-09-10 (4)）。
**最初から 64bit で計算する。**

**イネーブラで閉じている間もカウンタと割り込みは動き続ける。**
実機のイネーブラが止めるのはアドレスデコードだけで、ブロックを停めるわけではない。

#### 実装（Phase 1-5、2026-09-12）

`Src/Memory/romMapperY8960Timer.c`。**openMSX_Y8960 の `MSXTimer` の移植**で、
数え方はそのまま持ってきた。

**カウンタは分周前のクロックで数える。** 分解能を変えても、カウンタが
どこまで進んでいたかが失われない。読み出すときに `2^(10 + 2 * reso)` で割る。

**桁上がりの手前に起床点を張る**。`boardTimerAdd()` で、分周後のカウンタが
次に 1 増える時刻に起こしてもらう。openMSX の同期ポイントと同じ考え方。

**掛け算は 64bit で行う。** 終端値 255・分解能 7 のとき `256 << 24` になり、
32bit では 0 に落ちる。0 になると起床点が消えてカウンタが止まる
（openMSX 側が 2026-09-10 に踏んだ）。

**止まっている間も時刻だけは進める。** そうしないと、有効にした瞬間に
それまでの経過が一気に流れ込む。

| ポート | 読み | 書き |
|---|---|---|
| B0h | レジスタ番号 | レジスタ番号（bit3-2 がカウンタ、bit1-0 がレジスタ） |
| B1h | 選択したレジスタ | 同左 |
| B2h | 4 本の割り込みフラグ | 立っているビットのフラグをクリア |
| B3h | 選択したカウンタ | カウンタ選択 |

レジスタ 0 は bit0 が繰り返し、bit6-4 が分解能、bit7 が割り込み許可。
レジスタ 1 が終端値。レジスタ 2 は bit0 が動作、bit1 でカウンタをクリア。

**割り込みは `boardSetInt(0x1000)`。** このビットは他のどのデバイスも
使っていない（**確認済み(読解)**: `boardSetInt` の呼び出しを全部見た）。

**イネーブラが閉じている間もカウンタと割り込みは動く。** 実機のイネーブラが
止めるのはアドレスデコードだけなので、閉じるのは I/O ポートの応答だけにした。

#### 確かめたこと（**確認済み** 2026-09-12）

テスト ROM に 3 つ足した（`tests/banktest.asm`）。

| | 内容 |
|---|---|
| 5 | イネーブラを開くまで `B2h` が答えず、`7FFFh` に `80h` を書くと答えるようになる |
| 6 | カウンタが進む |
| 7 | 終端値に達すると割り込みフラグが立ち、`B2h` への書き込みで消える |

**7 つとも OK。判別力も確かめてある** — `y8960IoEnabled()` が常に真を返すように
壊すと、**5 番だけが NG になり、6 と 7 は OK のまま**だった。

**5 番は I/O イネーブラと MMIO 窓の検証でもある。** §5.8 で
「反応するブロックが要る」と書いた宿題が、ここで片付いた。
`7FFFh` への書き込みが窓を通ってイネーブラに届き、
それがタイマーのポートを開けている。

**CPU への割り込みも確かめた**（`banktest` の 19、§11 の (23)）。H.KEYI にハンドラを
差し、VDP のフレーム割り込みを止めた状態で、待ちループ（`delay`）の間に 2 回以上呼ばれることを見る。

### 5.6 MSX-MIXER【入口まで実装 2026-09-12】

**このブロックは実機側で未実装である。**

| 分かっていること | 出所 |

| `B6h`-`B7h` が MSX-SOUND MIXER | `doc/fpga/.../doc/ioport.txt` の記載のみ |
| RTL のアドレスデコーダにも top にも**無い** | `hardware-notes.md` §7.4 |
| マニュアルの「レジスタ一覧」が**未記入** | 同 §8。MSSX 側も同じ理由で待っている（§3.3） |

**したがってレジスタが何を意味するか分からない。** §5.6 の当初方針どおり、
**値を憶える入口までを作った**（`romMapperY8960Mixer.c`）。

| | |
|---|---|
| I/O | `B6h` がレジスタ番号、`B7h` がデータ。**ライトオンリー** |
| レジスタ | 256 バイト。書かれた値を憶えるだけで、何にも繋がっていない |
| イネーブラ | **無い。** イネーブラ 2 はビットを OPL2 ×2・DCSG ×2・SSGS・タイマに割り当てており、ミキサーには何も無い（§5.8） |
| トンネル | **無い。** 窓のデコードは `7FEAh`-`7FF5h` だけで、ミキサーは入っていない |
| セーブステート | `y8960mixer` |

**読み出しを持たせなかった。** 応答するという記述がどこにも無く、
このカートリッジの他の未文書ブロック（OPLL / DCSG / カートリッジ版 SSGS）も
ライトオンリーである。**重ね合わせは AND なので、持たないポートを駆動すると
本来の持ち主を引き下げる**（§4.2）。

**`B6h`-`B7h` は他のどのデバイスとも重なっていない**（**確認済み(読解)**
2026-09-12: `ioPortRegister(0xb6` / `0xb7` の検索が 0 件。RTC は `B4h`/`B5h`）。

#### ゲインを各ブロックへ渡す仕組みは、まだ作れない

§4.3 のとおり blueMSX のミキサーにはデバイス単位のゲイン API が無いので、
**各ブロックが自分の出力に自分で左右ゲインを掛ける**形になる。
渡し方は §9.3 に 2 案あるが、**どちらを選ぶかが今の律速ではない。**

**レジスタからゲインへの対応が存在しないので、渡すべき値が無い。**
いま配線を通しても、全ブロックが恒等倍を掛けるだけの死んだ経路になり、
**判別力のある試験を書けない。**

**やり直しの値段**: レジスタ仕様が来たら、この箱に対応表を足し、
§9.3 の渡し方を 1 つ選び、**5 ブロックの sync に 1 行ずつ**掛け算を入れる。
器を先に作っても後から作っても、触る場所は同じ 5 か所である
（掛け算の位置がブロックごとに違うため、共通化できない）。

**出力の切り替え**（Y8960 だけ / 本体だけ / 両方）は openMSX 側に在る機能だが、
blueMSX+ でどう出すかは **未決**（§9.4）。

#### 確かめていないこと

**このブロックは外から観測できない。** 値を憶えるだけで、音にも読み出しにも
出ない。**MSX 側から確かめる手段は無い**ので、確かめていない。
デバッガのレジスタバンクに出ることだけが見る手段である（**未検証**）。

### 5.7 Y8960 SCC（バンクメモリ）

**土台は `Src/SoundChips/SCC.c` をフォークした `Src/SoundChips/Y8960Scc.c`
＋ 新規マッパー `Src/Memory/romMapperY8960Scc.c`。**
カートリッジ内の回路はコナミの SCC そのものではなく等価回路（ハードウェアでは
IKASCC）なので、本体のコアを共有しない（§11 2026-09-12 (10)）。

マッパーの規則は openMSX_Y8960 の implementation-plan §3.8.1 で確定している。
**その 4 規則をそのまま移す。**

| | 規則 | 出所 |
|---|---|---|
| 1 | SCC 音源レジスタは、その region 自身のバンクレジスタが 3Fh のとき、その region の 1800-1FFF に出る。**RAM モードのバンク0 だけは出さない** | openMSX 側の判断。**ファームウェアが使うのは BANK1 の 7800h だけ**なので、残る region は余分に出しているだけ（§3.3） |
| 2 | MMIO 窓は、**バンク1 が ROM を出しているときだけ**出る。**RAM とみなすのは RAM モードの `#16`-`#31` だけ**で、互換モードでは `#16`-`#31` でも出る | **2026-09-12 にユーザーが確定**（§9.5）。RAM モードの条件は openMSX_Y8960 に揃えた（§11 の (22)） |
| 3 | RAM モードのバンク0 は書き込み不可。**RAM バンクを出していても書けない** | openMSX 側の既存実装の踏襲 |
| 4 | バンク 3Fh を RAM バンクとして扱わない | バグ修正。`#16` 以上を RAM と判定すると `3Fh` も通ってしまう |
| 5 | `4000h`-`7FFFh` のバンクは `C000h`-`FFFFh` にも、`8000h`-`BFFFh` のバンクは `0000h`-`3FFFh` にも読める | openMSX_Y8960 に揃えた（§11 の (22)） |

外に出る値は `hardware-notes.md` §3 / §4 と openMSX_Y8960 の §4.4 にある。

| 値 | |
|---|---|
| RAMMODE レジスタ | 48FBh（ミラー 49FBh-4FFBh） |
| RAM モードのバンクレジスタ | 48FCh-48FFh（同上） |
| 互換モードのバンクレジスタ | 5000-57FFh / 7000-77FFh / 9000-97FFh / B000-B7FFh |
| SCC 音源レジスタ | 各 region の 1800-1FFF |
| SCC 窓を開くバンク値 | 3Fh |
| MMIO 窓 | 7FE0-7FFFh（書き込み専用） |

**メモリ構成は決まった**（§3.3 / §9.5）。**256KB を 8KB × 32 バンクに区切り、
`#0`-`#15` が ROM、`#16`-`#31` が RAM。** MSSX のファームウェアがこれを前提に
動くので、RTL にバンク番号の分岐が無いのは WIP だからだと見てよい。

`y8960bas.rom` は 128KB = ROM バンク `#0`-`#15` にちょうど収まる。

窓の初期値は BANK0=`#0`, BANK1=`#1`, BANK2=`#2`, BANK3=`#3`
（**確認済み(読解)**: MSSX の `docs/y8960/hardware.md`。写しの §4 とも一致）。

**MMIO 窓は BANK1 に ROM バンクが出ているときだけ表に出る。**
RAM バンクまたは SCC (`3Fh`) のときは隠れる（§9.5。2026-09-12 にユーザーが確定）。
**RAM バンクとみなすのは RAM モードのときだけ**で、互換モードで `#16`-`#31` を
出しても窓は出る（§9.5）。

#### 実装（Phase 1-1、2026-09-12）

`Src/Memory/romMapperY8960Scc.c`。**256KB を単一の配列で持ち、
`bankReg[region] & 0x1F` でアドレスを決める。** 実機（RTL）が
`bankreg[4:0]` の 5bit しかアドレスに出さないのと同じ形で、
前半 128KB が ROM、後半 128KB が RAM に当たる。

**バンクレジスタは 6bit 保持する。** アドレスに出るのは 5bit だが、
`3Fh` が SCC 窓を選ぶので上位ビットを捨てられない。

**openMSX_Y8960 の規則 4（バンク 3Fh を RAM バンクとして扱わない）は、
こちらでは要らない。** あちらは ROM と RAM を別オブジェクトで持つため
`bank - 16 = 47` が範囲外になったが、単一配列なら `& 0x1F` で
バンク 31 を指すだけで収まる。**RTL の挙動とも一致する。**

| 窓 | アドレス | レジスタ（互換モード） | レジスタ（RAM モード） |
|---|---|---|---|
| BANK0 | 4000-5FFF | 5000-57FF | 4?FCh |
| BANK1 | 6000-7FFF | 7000-77FF | 4?FDh |
| BANK2 | 8000-9FFF | 9000-97FF | 4?FEh |
| BANK3 | A000-BFFF | B000-B7FF | 4?FFh |

RAM モードのレジスタは `4?FBh`（? = 8..F）で、**両モードで常に見える**。

**書き込みの経路は 2 つある。** RAM モードで RAM バンクが出ている region は
`slotMapPage` の `writeEnable` を立てて直接書かせる。**region 0 だけは
`writeEnable` を立てない** — そこにレジスタがあるので、書き込みを
コールバックで受ける必要がある。**コールバックは region 0 への書き込みを
メモリに落とさない**（規則 3）。

#### 確かめたこと（**確認済み** 2026-09-12）

**テスト用のカートリッジ ROM を書いて、MSX 側からレジスタを叩いて確かめた。**
`tests/banktest.asm`。ROM の init から走るので、Y8960 のスロットが
選択された状態で始まり、スロット切り替えが要らない。C-BIOS でも動く。

各バンクの `0C00h` にバンク番号を置いた 128KB の ROM を用意し、3 つを見る
（最初は `0800h` に置いていたが、テストのコードが伸びて届いたので移した）。

| | 内容 | 結果 |
|---|---|---|
| 1 | 互換モードで BANK1 に ROM バンク 0-15 を順に出し、各々が自分の番号を返すこと | **OK** |
| 2 | RAM モードで RAM バンクに書いた値が残り、**別のバンクには現れない**こと | **OK** |
| 3 | 互換モードでは書き込みが効かないこと | **OK** |

**判別力を確かめてある。** 実装を 2 通りに壊して、期待どおり落ちることを見た。

| 壊し方 | 1 | 2 | 3 |
|---|---|---|---|
| `bankSwitch` が常にバンク 0 を出す | **NG** | **NG** | OK |
| 書き込み許可を常に立てる | **NG** | **NG** | **NG** |
| （戻すと） | OK | OK | OK |

2 つ目の壊し方で 3 つとも落ちるのは、`slotMapPage` に書き込みを許すと
**バンクレジスタへの書き込みもコールバックに来なくなる**ため。
壊し方としては粗いが、3 番目に判別力があることは示せている。

**この検証は `Init ROM in slot:` の表示には一切依存していない。**

**まだ確かめていないこと**: SCC 窓、MMIO 窓、I/O イネーブラ、トンネル。
どれもまだ実装が無い。

#### SCC 音源の接続（Phase 1-2、2026-09-12）

上流の `sccCreate()` は音を `MIXER_CHANNEL_SCC` に固定で載せるので使えない。
**`SCC.{c,h}` を `Y8960Scc.{c,h}` にフォークし、`MIXER_CHANNEL_Y8960` に
固定で載せる**（§6.2）。公開シンボルだけ改名してある
（`SCC` → `Y8960SccChip`、`sccXxx` → `y8960SccXxx`、
`SccMode` → `Y8960SccMode`、`SCC_REAL` → `Y8960_SCC_REAL`）。
内部の変数名は上流のまま残してあるので、上流が直したときに差分を取れる。

**セーブステートの節名は `y8960scc` に変えてある**（理由は §5.4 と同じ）。

**SCC 窓が出ている region は、ページ全体をコールバック経由にする。**
窓は region の 1800-1FFF だけだが、`slotMapPage` は 8KB 単位でしか
読みを許可できないため。窓が閉じている region は従来どおり直接読ませる。

`read` と `peek` は分けてある。**SCC は `Mode::Real` でも読み出しで
deformation レジスタが発火する**ので、デバッガの覗き見（`peek`）が
音源の状態を変えてはいけない。

#### 確かめたこと（**確認済み** 2026-09-12）

`tests/banktest.asm` に 4 番目を足した。BANK1 に `3Fh` を書くと
`7800h` が SCC になり、書いた値が読み戻せる。バンク番号に戻すと
メモリに戻る。**4 つとも OK。**

**判別力を確かめてある。** `sccVisible()` が常に偽を返すようにすると、
**4 番だけが NG になり、1-3 は OK のまま**だった。

**音も確かめた**（**確認済み** 2026-09-13）。`sndtest` の F が BANK1 の SCC の
チャンネル 1 に 990 Hz の矩形波を鳴らし、録音から 990.9 Hz が読めた。
ユーザーも同じ実行を聴いて、SCC が鳴っていることを確かめた。§11 の (24)。

#### BANK2 / BANK3 はページ2 を切り替えてから試す

**カートリッジの init はページ1（4000-7FFF）だけがカートリッジのスロットに
切り替わった状態で走り、ページ2（8000-BFFF）は RAM のまま**である。
そのまま BANK2 / BANK3 に書いても、書き込みはマッパーに届かない。

**一度これで誤った OK を出した。** BANK2 に書いて読み返すテストが通ったが、
届いていたのは RAM で、同じ場所に書いて読んだだけだった
（**確認済み**: マッパーに記録を仕込み、`9000h` への書き込みが
一度も現れないことを見た）。

**`banktest` の 17 / 18 は A8h でページ2 をカートリッジのスロットにしてから試す**
（§11 の (23)）。窓の読み返しに加えて、RAM が持っていないバンクの印も読むので、
RAM に書いて読んだだけでは通らない。

#### ミラー（2026-09-12、openMSX_Y8960 に揃えた）

**マッパーが `4000h` から始まるときだけ**、ページ 0-1 と 6-7 も同じスロットに登録し、
`bankSwitch` が本体のページと一緒にミラーのページを写す。ミラーは常に
**読み込み可・書き込み不可**でコールバックを持たない。コールバックの無いページへの
書き込みは捨てられる（**確認済み(読解)**: `slotWrite`）ので、ミラーからは
バンクレジスタも SCC も MMIO 窓も叩けない。

| 本体のページ | ミラー |
|---|---|
| 2-3（`4000h`-`7FFFh`） | 6-7（`C000h`-`FFFFh`） |
| 4-5（`8000h`-`BFFFh`） | 0-1（`0000h`-`3FFFh`） |

**SCC を出している region のミラーは、SCC ではなくバンク `#31` のメモリを見せる**
（`3Fh & 1Fh`）。openMSX_Y8960 は ROM バンク `#15` を見せる。§11 の (22)。

**確かめたこと**: `banktest` の 15（ページ0 をカートリッジのスロットにして `0C00h` を
読み、BANK2 のバンク 2 の印が返る）と、16（ページ3 を同様にして `EC00h` を読み、
BANK0 と BANK1 の印が返る。`CC00h` と `EC00h`）。

### 5.8 I/O イネーブラとメモリマップド I/O のトンネル

この 2 つはブロックではなく、**Y8960 SCC のマッパーが持つ機能**である
（窓が 7FE0h-7FFFh にあり、マッパーがメモリ空間を見ているため）。

| 窓 | 内容 |
|---|---|
| 7FF6h | I/O Enabler 1。b0 = OPLL#1 (7Ch-7Dh)、b1 = OPLL#2 (7Ah-7Bh) |
| 7FFFh | I/O Enabler 2。b0/b1 = OPL2、b2/b3 = DCSG、b4 = SSG、b7 = MSX-TIMER |
| 7FEAh-7FF5h | 各ブロックへのトンネル。**イネーブラの影響を受けない** |

**窓そのものが出る条件は BANK1 の中身で決まる**（§9.5）。BANK1 に ROM バンクが
出ているときだけ表に出て、RAM バンクまたは SCC のときは**イネーブラごと隠れる**。
つまり **RAM バンクを BANK1 に出したままではイネーブラを書き換えられない。**
RAM バンクとみなすのは RAM モードのときだけである（互換モードの `#16`-`#31` では窓が出る）。

**リセット直後は全部閉じている**（**2026-09-13 にユーザーが確定**: カートリッジ版では
リセット直後にすべての I/O ポートが閉じている。RTL が `7Ah` 側と `A0h` 側をリセット時に
有効にしているのは、ハードウェアのデバッグのための一時的な措置）。

#### 本体内蔵の Y8960 には窓もイネーブラも無い

**2026-09-12 のユーザー指示**: 「本体内蔵の場合はイネーブラー無しで常に全音源の
ゲートが開いている。MMIO 自体が無い」。

**本体内蔵でも、バンクメモリと SCC は残る。消えるのは窓（とその中のイネーブラと
トンネル）だけである**（hra1129 さんの回答。openMSX_Y8960 の §3.6.1 に記載）。

エミュレータ側では**基盤タイプ `MSX2++` がそれ**を表す。`MSX.c` が機種を作る前に
`y8960SetBuiltIn()` で伝え、SCC ブロックは次のように振る舞う。

| | カートリッジ | `MSX2++` |
|---|---|---|
| 窓 `7FE0h`-`7FFFh` | BANK1 が SCC でも RAM モードの RAM バンクでもないとき出る | **出ない** |
| `y8960IoEnabled` | イネーブラの値 | **常に真** |
| バンクメモリ・SCC | 在る | **在る** |

**SCC ブロックを置かないカートリッジ構成でも `y8960IoEnabled` は真を返す。**
イネーブラへ届く手段が無いので、閉じたままにすると永遠に鳴らない。
これは仕様ではなくエミュレータの都合である。

#### `boardGetType()` では判定できない

**`boardGetType()` は `boardType & BOARD_MASK` を返す**ので、`MSX2++`（`0x0105`）は
MSX 系統の `0x0100` に丸められ、`BOARD_MSX2PP` と一致することが無い
（**確認済み(読解)**: `Board.c`。呼び出し 12 か所がこの丸めに頼っている）。
**最初はこれで判定して、試験が落ちた**（§11 の (21)）。
機種を作る側（`MSX.c`）は `machine->board.type` を直に見ているので、そこから伝える。

窓の中は**高位側が 1 番目**。直接 I/O 側とは並びが違う（`hardware-notes.md` §3）。
**片方から他方を推論してはならない。**

**イネーブラの実現方法は §4.2 を直したことで素直になった。**
ポートは重ねて登録できるので、Y8960 は自分の登録を常に持ったままにし、
**閉じているときは `writeIO` の中で書き込みを捨てる**だけでよい
（openMSX_Y8960 も同じ形にしている）。本体側が先に取っていても構わない。

`ioPortUnregister` でポートを出し入れする必要は無い。読み出しのある
ブロック（OPL2 と MSX-TIMER）は、閉じている間 `readIO` が `0xFF` を返せば
AND 合成で他のデバイスの邪魔をしない。

#### 実装（Phase 1-3、2026-09-12）

窓は `7FE0h`-`7FFFh`、**書き込み専用**。`RomMapperY8960Scc` が持つ。

**窓が出る条件は BANK1 の中身と RAM モードで決まる**（§9.5）。ROM バンクなら出て、
SCC なら消える。`#16`-`#31` は RAM モードのときだけ消し、互換モードでは出す。SCC 窓 `7800h`-`7FFFh` は MMIO 窓を
完全に含むので、両者は部分的に重ならず、条件が 1 本の式で書ける。

| アドレス | 内容 |
|---|---|
| `7FF6h` | I/O Enabler 1 |
| `7FFFh` | I/O Enabler 2 |
| `7FEAh`-`7FF5h` | 各ブロックへのトンネル（Phase 1-4） |

**イネーブラを他のブロックから読む口を先に作った。**
`romMapperY8960.h` の `y8960IoEnabled(Y8960IoBlock)`。
窓は SCC ブロックの持ち物なので、実体はそこにあり、
**カートリッジが 1 枚である前提でシングルトンにしている**（§9.3 と同じ判断）。

**SCC ブロックが構成に無ければ 0 を返す。** ブロックを単独でマシン構成に
置いたとき、イネーブラが無いからといって開きっぱなしにはしない。

**ミラーの `3FE0h`-`3FFFh` は実装していない。** 実機は `A14` を見ないので
両方に出る。バンクのミラー（§5.7）はページ0 にもあるが、書き込みを捨てるので
窓はそこに現れない。openMSX_Y8960 も持たない。

#### 確かめられないこと

**窓が出ていることは、外から見て確かめられない。**

| BANK1 | 窓 | `7FF6h` への書き込み | 読み返し |
|---|---|---|---|
| RAM バンク | 無い | ページが書けるので直接 RAM へ（マッパーに届かない） | 書いた値 |
| ROM バンク | 有る | イネーブラへ | ROM の値 |

**どちらの行も、窓の有無とは別の理由だけで説明が付く。**
RAM の側は「書ける RAM だから」、ROM の側は「ROM だから」で足りる。

**判別力の無いテストを 1 つ書いて、消した。** RAM バンクのとき `7FF6h` が
RAM として読み書きできることを見るテストを足したが、
`mmioVisible()` が常に真を返すように壊しても**通ったまま**だった。
書き込みがページ経由で直接 RAM に行き、窓の判定に届いていない。
テスト 2 の焼き直しでしかなかったので削除した。

**窓が出ていること自体は、マッパーの側に記録を置けば確かめられる**
（Phase 1-4 でそうした）。**MSX 側からは、この 2 行では区別できない。**
互換モードで `#16`-`#31` を出したときは書き込みがページに行かないので、
イネーブラ越しにタイマが開くかどうかで区別できる（`banktest` の 13）。

**イネーブラが効いていることは、Phase 1-5 の MSX-TIMER で確かめられた**（§5.5）。
タイマーが最初の「反応するブロック」になった。`7FFFh` への書き込みが
この窓を通ってイネーブラに届き、タイマーのポートを開けている。

#### トンネル（Phase 1-4、2026-09-12）

窓の `7FEAh`-`7FF5h` が各ブロックへの書き込み口になる。

**イネーブラの影響を受けない。** イネーブラ自身がこの窓の中にしか無いので、
トンネルまで閉じると開く手段が無くなる。

**ブロックは自分で名乗り出る。** `y8960RegisterTunnel()` で登録し、
破棄するときに `y8960UnregisterTunnel()` で外す。
**外せるのは登録した本人だけ**にしてある（`ref` を照合する）。
差し替えで新しいデバイスが登録した後に古い方が破棄されても、
新しい側の登録を剥がさない。誰も登録していないトンネルへの書き込みは捨てる。

#### 確かめたこと（**確認済み** 2026-09-12）

`tunnelWrite()` に記録を入れ、テスト ROM から `7FEAh` から 12 バイトに
`A0h` から順の値を書いた（`tests/banktest.asm` の `tunnels:`）。
**12 件すべてが表どおりの宛先に届いた。**

| アドレス | 宛先 | port |
|---|---|---|
| 7FEA / 7FEB | SSGS | 0 / 1 |
| 7FEC / 7FED | **OPL2 #1** | 0 / 1 |
| 7FEE / 7FEF | OPL2 #0 | 0 / 1 |
| 7FF0 / 7FF1 | DCSG #1 / #0 | 0 |
| 7FF2 / 7FF3 | OPLL #1 | 0 / 1 |
| 7FF4 / 7FF5 | OPLL #0 | 0 / 1 |

**窓が出ていることも、これで同時に確かめられた。** 窓が閉じていれば
`tunnelWrite()` は呼ばれない。**MSX 側からは区別できないだけで、
マッパーの側に記録を置けば見える**（§5.8 の「確かめられないこと」を
そう読み替えること）。

記録はコミットしていない。テスト ROM の掃き出しは残してあるので、
同じ確認をするときは `tunnelWrite()` に数行足せばよい。

**受け手はまだ無い。** 7 ブロックのどれも `y8960RegisterTunnel()` を
呼んでいないので、届いた先で何も起きない。**音が出るかどうかは Phase 2。**

| 185 | `ROM_Y8960SCC` | `Y8960SCC` | Y8960 SCC | SCC + マッパー + イネーブラ + 窓 |

| 187 | `ROM_Y8960` | `Y8960` | Y8960 Cartridge | 上の 7 つを一度に（カートリッジ専用） |

`ROM_MAXROMID` は **187** になる。

**187 はマシン構成には出さない。** マシン構成は 180-186 を個別に並べる設計で、
187 を足せる場所を作ると同じブロックが二重になる。`Win32machineConfig.c` の
`romTypeList` には入れていない（2026-09-20 に確定、§11 の (30)）。

**カートリッジ名は設定ファイルと履歴に保存されるので、後から変えられない。**
`CARTNAME_Y8960 = "Y8960 Cartridge"`。`RomTypeList.c` の `cartList` の注記が
そう書いており、変えると既に保存した `bluemsx.ini` と最近使ったファイルの一覧が
読めなくなる（**確認済み(読解)**: `Src/Emulator/RomTypeList.c:165-167`）。

**短縮名はコマンドラインにも出る。** `romTypeToShortString` の戻り値は
`/romtype1` / `/romtype2` が受け取る名前と照合され、`/listromtypes` で一覧される
（**確認済み(読解)**: `Src/Emulator/CommandLine.c:53-65` の
`romTypeFromShortString`）。テーマのトリガーでも使われる。

**やり直しの値段**: 数値を変えると、既に作った `config.ini` が全部ずれる。
短縮名を変えると、それを書いたコマンドラインとスクリプトが通らなくなる。
**表示名だけは言語リソースの中なので安く変えられる。**

#### RomType を足したら Win32machineConfig.c の 4 箇所に登録する

`Src/Win32/Win32machineConfig.c` の**選択肢リスト（`romTypeList`）に足しただけでは、
マシン構成エディタは開始ページを決められない。** `endEditControls` の switch には
`default:` があり、そこは `pageCount` しか決めない。新規エントリは追加時に
ゼロ初期化されるので、**startPage 0 のまま保存される**。
エディタの画面上は開始アドレス欄が空になるだけで、警告は出ない。

メモリにマップされる RomType を足すときは、次の 4 箇所すべてを見る
（**確認済み(読解)**: `Src/Win32/Win32machineConfig.c`）。

| 箇所 | 何が決まるか |
|---|---|
| `romTypeList` | 種別コンボに出るか |
| `endEditControls` の switch | **保存される startPage / pageCount** |
| `setEditControls` の「開始アドレス」列挙と switch | アドレス欄の表示・選択肢 |
| `getAddressControl` の列挙 | アドレス欄を読み戻すか |

`ROM_Y8960SCC` は 4000h 固定なので、`ROM_SCC` / `ROM_KONAMI5` と同じ組に入れて
startPage 2 / pageCount 4 を強制する（2026-09-20、§11 の (29)）。

## 8. 検証方法

**ここが openMSX 側と最も違う。** ただし、**当初書いた「blueMSX+ には
自動テストの手段が無い」は言いすぎだった**。2026-09-12 に実測して分かった
ヘッドレスの経路を以下に含める。

openMSX_Y8960 は Tcl スクリプトで自動回帰テストを 13 本持っており、
どれも「期待値を外した構成で落ちる」ことまで確かめてある。
**blueMSX+ に同じことはできない** — エミュレータを走らせながら
レジスタを叩くスクリプト機構が無いため（**確認済み(読解)**:
`Src/Emulator/CommandLine.c:330-383` のオプション表に、スクリプトを実行する
手段も、音を録り始める手段も無い。`/debugger` はデバッガのウィンドウを
開くだけである）。

### 8.1 ヘッドレスで確かめられること

`/listromtypes` `/listmachines` `/listspecials` `/listthemes` は、一覧を
標準出力に書いて `exit(0)` する。**エミュレータのウィンドウが作られる前**に
終わる（**確認済み(読解)**: `Src/Win32/Win32.c` の `commandLinePrintLists` と
4892 行の `exit(0)`。**確認済み**: 実行してもプロセスもウィンドウも残らず、
終了コード 0 と出力が返った）。

| 手段 | Y8960 で何に使えるか |
|---|---|
| `/listromtypes` | **§6.1 の RomType 7 枠が登録されたか。**表示名と短縮名もそのまま出る |
| `/listmachines` | **7 ブロックを置いたマシン構成が読めるか。** `config.ini` をパースし、ROM ファイルの実在まで見る。**板種別も見る**: 知らない値は機種ごと落とされるので、`MSX2++` が一覧に出ることは板種別が通った証拠になる（**確認済み** 2026-09-12: `MSX2+++` に書き換えると一覧から消えた） |

**`/machinedir` で作業ツリーの `Machines` を直接読ませられる**ので、
テスト用構成をコピーせずに試せる（**確認済み**）。

**Phase 0 の「器ができた」は、この 2 つで判定できる。**

#### 音源コアだけを取り出して測る

**フォークした音源コアは blueMSX に依存しないので、単体でリンクして走らせられる。**
ウィンドウも ROM も要らず、繰り返せる。

| | |
|---|---|
| `tests/opllex-bank-probe.c` | OPLLEX の 4 バンク切り替え、13 項目。ビルド手順はファイル冒頭 |
| `tests/opl2ex-probe.cpp` | OPL2EX の 4 波形・共有サンプル RAM・落としたレジスタ、14 項目。`tests/opl2ex-host-stub.c` と一緒に建てる |
| `tests/ssgs-probe.c` | SSGS の 2 系統・パンポット・持たないレジスタ、15 項目。`tests/ssgs-host-stub.c` と一緒に建てる |

**MSX 側のテスト ROM**。

| | |
|---|---|
| `tests/banktest.asm` | バンクマッパー・窓・ミラー・タイマ・DCSG・OPLLEX・OPL2EX・SSGS。`make-banktest.py` で 128KB に展開 |
| `tests/ssgstest.asm` | **`MSX2++` の SSGS が PSG として働くか、窓とイネーブラが無いか。** `make-ssgstest.py` で 16KB の素の ROM に。`MSX2++` の試験構成の Y8960 SCC に載せる |

**この形の試験は「バンクレジスタを無視しても通ってしまう」ことが無いように
組んである**: まず 4 つの音色表が互いに違うことを確かめ、
**その違う表を読みに行くかどうか**だけを見る。
表が同じなら試験は成立しないので、そこで落ちる。

**届かないもの**: I/O ポートの登録、イネーブラのゲート、窓のトンネル。
どれもエミュレータを起動しないと踏めない（§8.2）。

### 8.2 ヘッドレスでは確かめられないこと

**デバイスの生成は走らない。** `machineIsValid` は `config.ini` のパースと
ROM の実在までで、`machineInitialize()`（`romMapper*Create` を呼ぶところ）には
届かない（**確認済み(読解)**: `Src/Board/Machine.c:647-690`）。

したがって次は**エミュレータを実際に起動しないと分からない**。

- **I/O ポートの登録が通ったか**（§4.2 の先勝ちで黙って落ちていないか）。
  これは Y8960 で最も危ないところなので、**起動しての確認が要る**
- 音が出るか、レジスタの挙動

| 手段 | 何ができるか | 未確認な点 |
|---|---|---|
| GUI で手動操作 | すべて。ただし人の手が要る | — |
| 音声ログ | `mixerStartLog()` が WAV を書く（**確認済み(読解)**: `AudioMixer.c:630`、UI からは `Actions.c:406`）。コマンドラインオプションは無いが、ウィンドウへの `WM_COMMAND` で開始・停止できる（**確認済み**、`doc/fork/build/README.md` §5.2） | — |
| MSX 側のテストプログラム | レジスタを叩いて結果を見る。BASIC 拡張やアセンブリで書く。結果は画面に出し、`PrintWindow` か画面の写しのコマンドで取り出す（**確認済み**、同 §5.1）。キーは `WM_COPYDATA` で押せる（同 §5.3） | — |
| デバッガプラグイン | メモリと I/O を覗く | 使っていない。自動化できるかは未確認 |

**起動するとウィンドウが出る。走らせる前に一声かけること。**

**非回帰テストの注意**（openMSX 側と同じ）: 修正後に通ることは、
**修正前に落ちることを示すまで証拠にならない。**
テストを書いたら、まず期待値を壊して落ちるのを確認する。

**実機が無いので「実機と一致」は検証できない。** できるのは
「openMSX_Y8960 と同じ挙動になること」までである。
openMSX 側は実測済みなので、**同じレジスタ列を与えて音を比べる**のが
最も確度の高い突き合わせになる。

### 8.3 最も強い検証 — ファームウェアを走らせる

**Y8960 を駆動する BIOS と拡張BASIC が実在する**（§3.3）。
madscient/MsxSoundSuiteExtension の `y8960bas.rom`、**128KB**。

**これは openMSX_Y8960 が持っていなかったものである。** あちらの
`hardware-notes.md` §8 は「BIOS ROM イメージが存在しない」と書いている
（hra1129/Y8960_Cartridge には無い、という意味では今も正しい）。

Y8960 SCC のマッパー（§5.7）が動けば、**この ROM を載せて起動できる**。
128KB は ROM バンク `#0`-`#15` にちょうど収まる。

**ファームウェアが起動して音が出れば、それは次のすべてが同時に通ったことを
意味する。**

- バンクレジスタと窓のデコード（§5.7）
- メモリマップド I/O のトンネル（§5.8）
- I/O イネーブラ（同上）
- 叩かれた音源ブロックそのもの

**どの単体テストより射程が広い。** 逆に、落ちたときにどこが悪いかは
分からないので、単体の確認と併用する。

起動・キー入力・画面と音の取得は自動化でき、`/hidden` ならウィンドウも出ない
（`doc/fork/automation/plan.md`）。**BASIC が要るので C-BIOS では走らない。**

**ROM はリポジトリに入れない**（§3.1）。実機の BIOS ROM と同じく、
gitignore 済みのビルド出力に置く（`doc/fork/build/README.md` §4）。

**前提**: MSSX 側も開発中である。Y8960 BASIC Extension と
Y8960 Sequencer BIOS は「（開発中）」と明記されている（**確認済み(読解)**:
MSSX の `README.md`）。**動かないときに、こちらが悪いとは限らない。**

### 9.9 本体内蔵版の SSGS — **決着済み（2026-09-12）**

### 9.5 SCC バンクメモリ — **決着済み（2026-09-12）**

§5.7 / §3.3。MSSX の記述と、**2026-09-12 のユーザーからの直接の回答**で
すべて決まった。**未決は残っていない。**

| | 決まったこと |
|---|---|
| ROM / RAM の境界 | **256KB、`#0`-`#15` が ROM、`#16`-`#31` が RAM。** ファームウェアがこれを前提に動く |
| SCC 窓 | **BANK1 に `3Fh` を書くと `7800h` に出る。** ファームウェアはここを使う |
| **MMIO 窓の出現条件** | **BANK1 に ROM バンクが出ているときだけ表に出る。RAM バンクまたは SCC のときは隠れる** |

**ROM 128KB + RAM 128KB の分割が正しい。** RTL にバンク番号による分岐が
無いのは、RTL が WIP だからだと見てよい（§2 の前提と整合する）。
**openMSX_Y8960 の既存実装（分割して持つ）が実機の意図に合っていた**ことになる。

blueMSX+ は**この境界で新規に書く**。openMSX 側が保留にしていた #2/#3/#5 は、
blueMSX+ では迷う必要が無い。

#### MMIO 窓の条件は BANK1 の中身だけで決まる

**2026-09-12 にユーザーから直接の回答があった**（最も強い出典）。

> BANK1 の MMIO は ROM が選択されている場合のみ表に出る。
> RAM または SCC が出ている時は MMIO は隠れる。

**`rammode` を直接見ない。** 見るのは BANK1 のバンクレジスタが何を指しているかだけ。

| BANK1 の中身 | MMIO 窓 |
|---|---|
| ROM バンク（`#0`-`#15`） | **出る** |
| RAM バンク（`#16`-`#31`） | 隠れる |
| SCC（`3Fh`） | 隠れる |

**上の表の「RAM バンク」は RAM モードのときの `#16`-`#31` を指す**
（2026-09-12、openMSX_Y8960 に揃えた。§11 の (22)）。互換モードで `#16`-`#31` を
出しても窓は出る。あちらの §3.8.1 が `!(ramEnabled && isRamRegion(3)) && bankreg1 != 3Fh`
と書いているとおりで、**「`rammode` を直接見ない」とした上の一文はこの範囲で改めた。**
互換モードでは `#16`-`#31` に書き込めないので、ユーザー回答の「RAM が出ている」には
当たらないと読む。

**前提**: 互換モードで `#16`-`#31` を出したときの窓の有無を、実機の仕様が別に定めないこと。
定めた場合は `mmioVisible()` の 1 式と `banktest` の 13、本節と §5.7 / §5.8 に波及する。

**MSSX の文書を「RAM モード 0 のとき**または**BANK1 に ROM」と読んだのは
誤りだった**（本書が 2026-09-12 に一度そう書いた）。RAM モード 0 であっても、
BANK1 が RAM バンクや SCC を指していれば MMIO は隠れる。

**前提**: MMIO 窓のアドレスが `7FE0h`-`7FFFh` から動かないこと。
動けば SCC 窓 `7800h`-`7FFFh` との包含関係が崩れ、条件が書き直しになる。

### 9.7 2 回路を 1 デバイスにするか 2 デバイスにするか — **決着済み。1 ブロック 1 デバイス（2026-09-12）**

OPLLEX / OPL2EX / DCSG は 2 回路ある。

- **1 デバイスが 2 回路を持つ**と、マシン構成に 1 行置けば 2 回路そろう。
  片方だけ載せる構成が作れない
- **2 デバイスを別々に置く**と、1 回路だけの構成が作れる。
  `config.ini` に 2 行書くことになり、`RomType` も 2 つ要る（§6.1 の表が変わる）

**「個別にマシン構成に追加できるようにする」という指示は、
ブロック単位を指していると読んだ**（ユーザーが挙げた一覧が回路単位ではなく
ブロック単位だったため）。

**この読みのまま §6.1 の `RomType` が確定し（2026-09-12 ユーザー判断）、
実装・試験・ユーザーガイドもその形で組んである。** OPLLEX と DCSG は 1 デバイスが
`chip[2]` を持ち、OPL2EX は 1 つのコアが 2 回路を持つ（**確認済み(読解)**:
`romMapperY8960Opllex.c` / `romMapperY8960Dcsg.c` / `romMapperY8960Opl2ex.c`）。
OPL2EX は 2 回路が ADPCM の 256KB を共有するので、分けるならその共有を
デバイスをまたいで持つ設計が別に要る。

**前提**: 2 回路を片方だけ載せた構成を作る必要が無いこと。必要になった場合は
`RomType` を 3 つ足し、3 つのマッパー、試験構成の `config.ini`、ユーザーガイド、
テストに波及する。

### 2026-09-20 (30) — 特殊カートリッジ「Y8960 Cartridge」。7 ブロックを一度に挿せるようにした

**きっかけ**: `Y8960 SCC` の ROM タイプで挿しても SCC ブロックしか入らず、
ほかの 6 ブロックはマシン構成からしか載せられなかった。

**決めたこと**（ユーザー判断）。

| | |
|---|---|
| スコープ | ROM イメージ無しでも、ROM イメージ付きでも同じ RomType で挿せる |
| 取り外し | SCC ブロックが他の 6 ブロックを所有し、排出時にまとめて壊す |
| 外部値 | `ROM_Y8960` = 187 / 短縮名 `Y8960` / 表示名・メニュー・`CARTNAME_Y8960` とも `"Y8960 Cartridge"` |

**排出と終了は別経路である**（**確認済み(読解)**）。ここが実装の勘所だった。

| 経路 | 何が呼ばれるか |
|---|---|
| 排出・入れ替え | `cartridgeInsert` 冒頭の `slotRemove` → **スロットの eject コールバック** |
| 本体の終了 | `deviceManagerDestroy` → **各デバイスの destroy を 1 回ずつ** |

終了時は `deviceManagerDestroy` が先に `shutDown` を立て、`deviceManagerUnregister`
が何もしなくなる（`Src/Memory/DeviceManager.c`）。つまり**一覧は縮まず、登録した
デバイスの destroy が必ず全部呼ばれる**。だから「SCC の destroy が他の 6 つも壊す」
にすると終了時に二重解放になる。カートリッジは `slotRemove` でしか外れず
（`boardRemoveExternalDevices` はディスクとテープだけ）、この 2 経路は交わらない。

そこで **eject コールバックだけを差し替えた**。`sccCreate` が `SlotEject` を引数で
受け、`romMapperY8960SccCreate`（従来どおり）は `destroy` を、
`romMapperY8960CartCreate`（カード一式）は 6 ブロックも壊す `ejectCart` を渡す。
デバイスマネージャに登録する destroy はどちらも `destroy` のまま。

6 ブロックには静的な実体ポインタと `romMapperY8960XxxDestroy()` を足した。
`Y8960 MSX-TIMER` は `theTimer` を既に持っていたので入口だけ。

**触ったもの**: `MediaDb.{h,cpp}`（187 と名前）、`Properties.{h,c}`（`CARTNAME_Y8960`
と特殊カートリッジ判定）、`RomTypeList.c`（`mapperList` と `cartList`）、
`MegaromCartridge.c`（`buf == NULL` と `buf != NULL` の両方）、
`romMapperY8960*.c` 7 本、`romMapperY8960.h`、`Win32Menu.c`（ID 41122・メニュー・処理）。

**確認済み**: VS2022 / Release / x64 でビルドが通った（エラー 0、警告 5 はいずれも
`Win32Cdrom.c` / `Win32Midi.c` / `Win32ShortcutsConfig.c` / `Win32file.c` の既存分で、
今回触ったファイルからは出ていない）。

**確認済み（走らせた、同日）。** 同じ `banktest.rom` を 2 通りの挿し方で走らせて
突き合わせた。試験構成 `MSX2+ - C-BIOS + Y8960 (whole cart)` は
`(banktest)` から 180-186 を抜いたもので、**Y8960 を一切持たない**。

| | 対照 | 本番 |
|---|---|---|
| 構成 | `(banktest)`（180-186 をマシン構成に並べ、185 に `banktest.rom`） | `(whole cart)` に `/rom1 banktest.rom /romtype1 Y8960` |
| 起動 16 秒の画面 | — | **対照とバイト一致**（PNG の MD5 が同じ） |
| 起動 62 秒の画面 | — | **対照とバイト一致** |
| 音（起動 2 秒から 64 秒、`/hidden` で WAV） | — | 200ms ごとの RMS 包絡が左 **0.9932** / 右 **0.9952** で相関。**片側だけ鳴っている区間は 0**、平均包絡の比 1.0041 |

**判別力は壊した版に掛けて示した。** 同じ `(whole cart)` に
`/romtype1 Y8960SCC`（＝SCC ブロックだけ）で同じ ROM を挿すと、

- 画面は **5 TIMER ENABLER: NG / 6 TIMER COUNTS: NG / 7 TIMER FLAG: NG /
  10 OPL2 READ BACK: NG**（1-4 の SCC ブロックは OK のまま）
- 音は **64 秒すべて無音**（平均包絡 0.0 対 486.2）

つまりこの突き合わせは、ブロックが入っていなければ落ちる。

**排出と終了も走らせた**（**確認済み**）。挿した状態で `ID_FILE_CART_REMOVE` を
送るとプロセスは生きたまま、続けて `WM_CLOSE` で終了コード 0。カートリッジを
挿したまま閉じた 3 回の実行もすべて終了コード 0。二重解放は起きていない。

**残る未確認**: MSX-MIXER が入っていること（`banktest` は MIXER を叩かない）、
ROM イメージ付きでファームウェア（`y8960bas.rom`）が起動すること。

**1 枚しか挿せない。** ブロックは静的な実体を 1 つずつ持つので、2 枚目を挿すと
1 枚目の排出が 2 枚目のブロックを壊す。マシン構成に 180-186 を並べたマシンへ
このカートリッジを挿した場合も同じブロックが二重になる（音量が倍になる）。
§10 に見送りとして記録した。

### 2026-09-20 (29) — マシン構成から挿した Y8960 SCC が動かない原因は開始ページだった

**症状**: マシン構成のメモリに `Y8960 SCC` を足して `y8960bas.rom` を割り当てると
動かないが、同じ ROM を同じ ROM タイプでカートリッジスロットに挿すと動く。

**原因**（**確認済み(読解)**）。マッパーを作る関数は両経路で同じだが、開始ページの
渡し方が違う。

| 経路 | startPage |
|---|---|
| カートリッジ | `MegaromCartridge.c` が **2 を決め打ち** |
| マシン構成 | `Machine.c` が `config.ini` の値をそのまま渡す |

そして `Win32machineConfig.c` は `ROM_Y8960SCC` を選択肢リストに持つだけで、
`endEditControls` の switch に case が無く `default:` へ落ちる。`default:` は
`pageCount` しか決めないので、**新規エントリのゼロ初期化のまま startPage 0 で
保存される**。アドレス欄を埋める列挙にも `getAddressControl` にも入っていないため、
画面から 2 を選ぶこともできない。

startPage 0 だとカード全体が 2 ページ下にずれる。リージョンは 0000-7FFF、
バンク・モードレジスタは 0?FBh、MMIO 窓は 3FE0h。コールバックに渡るアドレスは
`slotRead`/`slotWrite` が `address -= startpage << 13` した相対値なので
（`Src/Memory/SlotManager.c`）内部のデコードは動き、**位置だけが黙ってずれる**。
ミラーは `startPage == 2` のときだけ張られるので、そちらも落ちる。

**直した**: `Win32machineConfig.c` の `endEditControls` と `setEditControls` の
`ROM_SCC` / `ROM_SCCPLUS` と同じ case 群に `ROM_Y8960SCC` を入れた。
前者で startPage 2 / pageCount 4 が強制され、後者でアドレス欄に
`0x4000 - 0xBFFF` が出て灰色になる。**確認済み**: VS2022 / Release / x64 で
ビルドが通った（警告 0・エラー 0）。**エディタで実際に追加して動かす確認は
していない（未検証）** —— ウィンドウが出るので人間の合図が要る（§8.2）。

`doc/fork/y8960/tests/` の既存構成は最初から `1 0 2 4 185` と手で書いてあり、
影響を受けない。手で書いた構成が正しく、GUI から足した構成だけが壊れていた。

**同じ形の落とし穴が MSX-AUDIO にもあるかを調べたが、別物だった**（**確認済み(読解)**）。
`ROM_MSXAUDIO` は `endEditControls` で startPage 0 / pageCount 8 を明示的に
与えられており、カートリッジ経路の決め打ち 0 と一致する。同梱の
`MSX2+ - Sony HB-F1XV+` / `MSX2+(Custom)` が `0 1 0 8 50` / `0 2 0 8 50` で
成立していることからも、マシン構成経路そのものは通っている。
代わりに目に付いたのは次の 2 点で、**どちらも再現は取っていない（未確認の候補）**。

- `romMapperMsxAudioCreate` の `ioBase = 0xc0 + deviceCount++ * 2` は
  `ROM_MSXAUDIODEV`（romType 80、ROM なし）とカウンタを共有する。80 のエントリは
  整列キー 0 で必ず先に作られるので、80 を残したまま 50 を足すと ROM 付きの方が
  C2h/C3h に回る。**同梱構成 23 本を調べたところ、50 と 80 が同居するものは
  一つも無い**（**確認済み**: `Machines/*/config.ini` の全件走査）
- このマッパーはそのサブスロットの 8 ページ全部を占有する。同梱の成立例は
  いずれも空きサブスロットを丸ごと与えている

```
11 OPL2 (LISTEN): A SINE / B HALF SINE / C 2ND CIRCUIT / D TUNNEL, SHUT
```

#### 読み戻せるので、耳を使わずに 4 つ確定した

OPLL と DCSG は書き込み専用なので合否を画面に出せなかった。
**OPL2EX は読み戻せる**ので、10 の中で 4 段階を機械判定にできた。

| | 何を確かめたか |
|---|---|
| **a** | イネーブラを閉じるとデータポートが `FFh`（＝応答しない） |
| **b** | 開けると書いたレジスタが読み戻る |
| **c** | **閉じたままトンネルに書き、開けてから読んで一致。** 書いた口と読んだ口が別なので「往復しただけ」ではない。直前の値と違う値を書くので、届かなければ直前の値が残る |
| **d** | **2 回路目が別のチップ。** 回路 2 に書いた後も回路 1 は自分の値を保つ |

**耳が要るのは「レジスタが音になるか」だけになった。**
11 の B（A と違う音色）で波形レジスタ `E0h` が音に出ることを確認した。

#### 音を聴いて初めて分かった不具合が 1 件。ただしテスト ROM の側

**D の音が鳴りっぱなしになった**（ユーザーの指摘）。
10 が全部 OK だったので、届いていないのではないと分かっていた。

**原因はテスト ROM のレジスタ列**だった。コアに同じ列を直接与えて測った。

| 組み合わせ | 発音中 | key-off 後 |
|---|---|---|
| ROM が送っていた列（EG=0, RR=0） | 15346 | **15335 — 止まらない** |
| 速いリリースだけ（EG=0, RR=15） | **118 — すぐ消える** | 0 |
| **持続音 + 速いリリース（EG=1, RR=15）** | **15346** | **59 — 止まる** |
| 持続音 + 遅いリリース（EG=1, RR=0） | 15346 | 15335 — 止まらない |

**2 つのビットが両方とも要る。** 片方だけでは「鳴らない」か「止まらない」の
どちらかになる。直して走らせ直し、止まることを確認した。

**機械判定が全部通っていても、耳でしか分からないことは残る。**
ただしこの件は**エミュレータではなくテスト ROM の欠陥**だった。
10 が通っていたので、切り分けはコアに同じ列を与えるだけで済んだ。

|---|---|

### 2026-09-12 (5) — ADPCM の RAM は 4 状態をとる

**2026-09-12 にユーザーから直接の回答があった。**

サンプル RAM を回路の外に 1 つ持ち、各回路が見る範囲をモードで決める形に

- **emu2413 には YM2423 (OPLL-X) の音色データが無い**（3 セットのみ）。
  §5.2 / §9.2
- **`ioPortRegister` は 1 ポート 1 デバイスで、先勝ち、失敗は黙る。**
  そして本体 PSG はスロットデバイスより**後**に登録される。
  Y8960 の SSGS をマシン構成に置くと本体 PSG が壊れる。§4.2 / §9.1
- blueMSX のミキサーにデバイス単位のゲイン API が無い。§4.3
- blueMSX+ にスクリプトによる自動テストの手段が無い。§8
