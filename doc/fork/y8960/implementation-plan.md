## 1. 目的とスコープ

Y8960 カートリッジ（hra1129/Y8960_Cartridge）を blueMSX+ でエミュレートする。

**Y8960 を構成するデバイスブロックは、個別にマシン構成へ追加できるようにする**
（2026-09-12 ユーザー指示）。カートリッジ一体ではなく、ブロックごとに独立した
`RomType` を持たせ、`Machines/<名前>/config.ini` の `[Slots]` 行に 1 行ずつ
書けるようにする。理由は Y8960 のハードウェアがまだ WIP であり、
**どのブロックが最終的にどう組み合わさるかが決まっていない**こと。

対象ブロックは 7 つ。

| ブロック | 相当チップ | 備考 |
|---|---|---|
| OPLLEX | YM2413 + チャンネル別音色バンク | 2 回路 |
| OPL2EX | YM3812 + ADPCM-B | 2 回路。レジスタ配置は Y8950 と同一 |
| SSGS | YMZ705/732 相当 | 内部に YM2149 相当が 2 系統、チャンネルごとパンポット |
| MSX-TIMER | 独自 | 4 本のカウンタ + 割り込み |
| MSX-MIXER | 独自 | ブロックごとの左右ゲイン |
| Y8960 SCC | Konami SCC + 独自マッパー | バンクメモリを含む |
| DCSG | SN76489 | 2 回路。**音源コアは blueMSX に既存** |

### スコープ外

- FPGA コンフィグ・SPI Flash・SRAM 初期化シーケンス。実機の起動手順であって、
  エミュレータでは初期化済みで持てばよい
- ADPCM メモリの構成切り替え（**実機側で設定方法が未実装**）。
  ただし**器は 4 状態ぶん作る**。実装するのは起動時の共有モードだけ（§5.1）
- BIOS ROM イメージ（存在しない）

#### 決着が付いたもの

| # | 論点 | 写しでの状態 | MSSX の記述 |
|---|---|---|---|
| 1 | **ROM / RAM バンクの境界** | 出典 4 つが 4 つとも違い、RTL にはバンク番号による分岐が無い（§7.3） | **256KB、`#0`-`#15` が ROM、`#16`-`#31` が RAM**。「RAM バンクを出しても初期状態では書き込みは効かない」 |
| 2 | **SCC 窓の位置** | RTL は 9800h と、RAM モード限定の 7800h | **BANK1 のバンクレジスタに `3Fh`。窓は `7800h`** |
| 3 | **MMIO 窓の出現条件** | RTL は `memory_io_en = ~rammode` | **BANK1 に ROM バンクが出ているときだけ。RAM バンクまたは SCC のときは隠れる**（2026-09-12 にユーザーが確定。§9.5） |

| 5 | **OPLL の I/O Enabler のビット** | RTL と xlsx が逆（§6.1） | **b0 = OPLL1 (7Ch-7Dh)、b1 = OPLL2 (7Ah-7Bh)** |

**#5 は openMSX_Y8960 の判断が正しかったことの裏付けである。** あちらは
RTL を取り違えとして採らず、FM-PAC を正として b0 に 7Ch-7Dh を割り当てた。
ファームウェアも同じ割り当てで書かれている。

**#2 も同じ形で裏付けられた。** 従来の実装は SCC を 9800h にしか出しておらず、
openMSX_Y8960 が 4 つの region すべてに広げた（あちらの §3.8.1 規則 1）。
**ファームウェアは 7800h を使うので、9800h だけの実装では動かない。**

**#3 は openMSX_Y8960 の規則 2 と一致する。** あちらは
`!(ramEnabled && isRamRegion(3)) && bankreg1 != 3Fh` と書いており、
**BANK1 が ROM のときだけ窓を出す**という同じ条件になる。

**訂正**: 本書は当初、MSSX の文を「RAM モード 0 のとき**または** BANK1 に ROM」
という 2 条件の or と読み、RAM モード 0 で BANK1 が SCC のときに食い違うと
書いた。**これは誤読だった。** 2026-09-12 のユーザーからの回答で、
**見るのは BANK1 の中身だけ**と確定した（§9.5）。

## 4. blueMSX+ の作法（調査結果）

すべて **確認済み(読解)**。2026-09-12 に当該ファイルを読んだ。

### 4.1 デバイスの足し方

blueMSX のデバイスは `RomType`（`Src/Media/MediaDb.h` の enum、現在
`ROM_MAXROMID = 179`）で識別される。1 ブロックを足すのに触るのは次の 6 か所。

| 場所 | 何を足すか |
|---|---|
| `Src/Media/MediaDb.h` | enum の値。`ROM_MAXROMID` も更新 |
| `Src/Media/MediaDb.cpp` | `mediaDbStringToType`（DB の XML 名 → enum）、`romTypeToString`（表示名）、`romTypeToShortString`（短縮名） |
| `Src/Board/Machine.c` | 生成。ROM を伴わないデバイスは前半のループ、伴うものは後半の `switch` |
| `Src/Memory/romMapper<名前>.c` | 実装本体 |
| `Src/Win32/Win32machineConfig.c` | マシン構成エディタの一覧と、ROM ファイルを要求するかどうかの分岐 |
| `Src/Language/` | `romTypeToString` が返す表示名の文字列 |

**`config.ini` に書かれるのは enum の数値**である（**確認済み(読解)**:
`Machines/*/config.ini` の `[Slots]` 行は
`スロット サブスロット 開始ページ ページ数 romType "ROMファイル" ""` の形）。
したがって数値を後から変えると、既に作ったマシン構成ファイルが全部ずれる。

**ROM を伴わないデバイスの最小形**は `Src/Memory/romMapperTurboRTimer.c`（135 行）が
そのまま雛形になる。`deviceManagerRegister(romType, &callbacks, ref)` で
destroy / reset / saveState / loadState を登録し、`ioPortRegister` でポートを取る。

### 4.2 I/O ポートの重ね合わせ — **上流を直した（2026-09-12）**

**直す前の状態**（**確認済み(読解)**）。`ioPortRegister` は 1 ポートに 1 デバイス
しか登録できず、**既に誰かが登録していると黙って無視していた**。
戻り値が無いので呼び出し側は気づけない。

Y8960 は**設計上、本体デバイスと同じポートに重なる**ブロックを持つ。

| ポート | Y8960 | 本体側 | 重なりの意図 |
|---|---|---|---|
| A0h-A2h | SSGS | PSG | **設計どおり**。カートリッジ版 SSGS は本体 PSG に重ねて発音するだけの存在で、読み出しは本体 PSG が担う（`hardware-notes.md` §2） |
| 7Ch-7Dh | OPLL #1 | MSX-MUSIC | 機種による |
| C0h-C3h | OPL2 #1/#2 | MSX-AUDIO | 機種による |

しかも `Src/Board/MSX.c:253-259` は **`machineInitialize()` でスロットのデバイスを
作ってから `msxPsgCreate()` を呼ぶ**ので、マシン構成に置いた Y8960 SSGS は
本体 PSG より先に登録され、**本体 PSG の A0h / A1h 登録が黙って落ちていた**はずだった。

**2026-09-12 のユーザー判断により、これをエミュレータの不具合として上流を直した。**
実機のバスでは複数のデバイスが同じポートに応答しうる。

#### 直した内容

`Src/Memory/IoPort.c` と `IoPort.h`。

| | |
|---|---|
| 登録 | 1 ポートあたり **`IO_PORT_MAX_CLAIMS` (= 4) 件**まで持てる。同じ `ref` の再登録は上書き |
| 書き込み | **登録されたすべてに配る** |
| 読み出し | **駆動するものすべての AND**。実機で複数のカードが同時に応答したときと同じ |
| 解放 | **`ioPortUnregister(port, ref)` に `ref` を足した。** 自分の登録だけが消える |

**ハンドラの実行中に構成が変わりうる**（I/O イネーブラがまさにそれをする）ので、
配る前にエントリをローカルへ写してから呼ぶ。

`ioPortRegister` の呼び出し側（207 箇所）は**無変更**。
`ioPortUnregister` は**シグネチャが変わったので 53 ファイル 200 箇所を直した**。
`ref` は各 destroy 関数の中にあるデバイスポインタで、
**同じファイル内で同じポートを登録している行の第 4 引数**から機械的に決めた。

#### 直した副作用として、既存の不具合が 3 件見つかった

**どれも「1 ポート 1 デバイス」の下では実害が出にくく、重ね合わせを許すと
実害になる**もの。いずれも **確認済み(読解)**。

| ファイル | 何が起きていたか |
|---|---|
| `Src/Memory/romMapperKanji12.c` | **他人のポートを解放していた。** 自分は `0xF7` のサブポートしか登録しないのに、destroy で `0xD8`-`0xDB` を解放していた。それは `romMapperKanji` のもの。該当行を削除した |
| `Src/Memory/romMapperOpcodeModule.c` | **登録したポートを解放せず、登録していないポートを解放していた。** 登録は `0x40` / `0x50`-`0x52`、destroy は `0x60`-`0x6F`。登録した側を解放するように直した |
| `Src/IoDevice/Sf7000PPI.c` | `0xE0` / `0xE1` の解放漏れ。2 行足した |

`ioPortGetRef()` で「自分が登録できたか」を確かめてから解放していた 2 箇所
（`romMapperKorean90.c`、`romMapperMsxAudio.c`）は**ガードを外した**。
`ref` で解放するようになった以上そのガードは不要で、**残すと有害**である —
自分が 2 番目の登録だと `ioPortGetRef` は他人の `ref` を返し、
解放されないまま残る。

#### 確度

**ビルドは通っている**（**確認済み**: 0 エラー。`doc/fork/build/README.md` の手順）。
**挙動は未検証** — エミュレータを起動して確かめていない。
`/listromtypes` と `/listmachines` は変更前と同じ結果を返すが、
**この 2 つはデバイス生成を走らせないので I/O の検証にはならない**（§8.2）。

**起動しての確認が要る。** 見るべきは次の 2 点。

1. **既存機種が壊れていないこと。** これまで黙って落ちていた登録が有効になるので、
   重なっていた組があれば挙動が変わる
2. **重ね合わせが実際に効くこと。** Y8960 が無い今は、
   ルートの `README.md` が「未対応」と書いている
   MegaFlashROM SCC+ SD のカートリッジ側 PSG が試せる見込み（**未確認** — 
   その機能がこの制約だけで止まっていたのかを確かめていない）

### 4.3 サウンドの出し方

`mixerRegisterChannel(mixer, audioType, stereo, updateCb, rateCb, ref)` で登録する
（**確認済み(読解)**: `Src/SoundChips/AudioMixer.h:108`）。`stereo` に 1 を渡せば
ステレオのデバイスにできる（`AY8910.c:281` が実例）。

**blueMSX のミキサーには、デバイス単位のゲイン／パンを外から与える API が無い。**
`mixerSetChannelTypeVolume` / `mixerSetChannelTypePan` はいずれも**チャンネル種別**
単位である（**確認済み(読解)**: `AudioMixer.h:84-88`）。openMSX の
`MSXMixer::setDeviceGain()` に当たるものが存在しない。

したがって **MSX-MIXER のゲインは、各ブロックが自分の出力に自分で掛ける**形になる。
§5.6 に設計を書く。

### 4.4 ビルド定義

ファイルを足したら 3 か所に反映する（**確認済み(読解)**: `blueMSX/Make/` 配下）。

| 場所 | |
|---|---|
| `Make/msvc2022/blueMSX.vcxproj`（+ `.filters`） | MSVC 2022 |
| `Make/msvc2026/blueMSX.vcxproj`（+ `.filters`） | MSVC 2026 |
| `Make/gcc/` | GNU make |

**どれも明示列挙である。自動収集は無い。** `Make/gcc/Makefile` は
`SOURCE_FILES += <ファイル名>` を並べる形で、ディレクトリは `vpath` で解決している
（**確認済み(読解)**: 同ファイル 91行目と 105行目以降）。vcxproj も列挙。
つまり**ファイルを 1 本足すごとに 3 か所（.filters を数えれば 5 か所）に書き足す**。

**CI が通しているのは `msvc2022`（v143）だけである**（**確認済み(読解)**:
`.github/workflows/ci.yml` が `blueMSX/Make/msvc2022` で msbuild を呼ぶ）。
ローカルもそれに揃えてある。`msvc2026`（v145）と GNU make は

## 5. ブロックごとの実装方針

すべて **未検証**（設計であって、書いても動かしてもいない）。
土台として挙げたファイルを読んだことは **確認済み(読解)**。

### 5.1 OPL2EX（YM3812 + ADPCM-B）×2

**土台は `Src/SoundChips/OpenMsxY8950Latest/` のフォーク。**

blueMSX+ は openMSX の最新 Y8950 を既に移植して持っている
（**確認済み(読解)**: `OpenMsxY8950Latest.h` の冒頭が
「Ported from openMSX's latest Y8950 (MSX-Audio)」と書いており、
`OpenMsxY8950Latest/` に openMSX 側の原本 `Y8950.cc` / `Y8950Adpcm.cc` が
参照用として置かれている）。

**openMSX_Y8960 の `Y8960OPL2` は、まさにその openMSX `Y8950` のフォークである**
（`hardware-notes.md` 側ではなく openMSX_Y8960 の implementation-plan §3.4）。
したがって **blueMSX+ 側に当てるべき差分は、openMSX 側で既に作られている差分と
同じ**になる。

当てる差分は 3 つ。

| | 内容 |
|---|---|
| 波形選択 | `sinTable` から 4 面のテーブルを作り、スロットが `wave` と `waveTable` を持つ。E0h-F5h がスロットごとに選び、TEST レジスタ 01h の b5 が全体のゲート。リズム用スロットはサインを直接使う |
| 落とすレジスタ | キーボードコネクタ、13bit DAC、`Y8950Periphery`。05h, 06h, 0Dh, 0Eh, 15h-17h, 18h, 19h, 1Ah, 07h の b3 |
| ADPCM | `OpenMsxY8950LatestAdpcm` を共有する。openMSX 側は `Y8950Status` インターフェースを切り出して 2 チップで共有した。同じ手が使えるはず（**未検証**） |

#### ADPCM のサンプル RAM は 4 状態をとる

**2026-09-12 にユーザーから直接の回答があった**（最も強い出典）。

256KB を 2 回路でどう分けるかに **4 つの状態がある**。

| 状態 | |
|---|---|
| **共有** | 2 回路が同じ 256KB を見る |
| **片寄せ（回路 1）** | 256KB を回路 1 に割り当てる |
| **片寄せ（回路 2）** | 256KB を回路 2 に割り当てる |
| **分割** | 128KB + 128KB |

**設定の方法は実機側で未実装である。** どのレジスタで切り替えるかが決まって
いない（写しの §7.5 が「manual にあるがレジスタが無い」と書いていたのは、
この状態を指していたことになる）。

**起動時は共有モードという前提を置く**（ユーザーの暫定判断。
ハードウェア側で決まり次第、修正する）。**MSSX も共有モードで動く前提**である。

**したがって器は 4 状態ぶん作る。** 実装するのは共有モードだけだが、
サンプル RAM を**回路の外に 1 つ持ち、各回路が見る範囲をモードで決める**形に
しておけば、切り替えレジスタが決まったときに足すのは分岐 1 つで済む。
回路ごとに RAM を持たせてしまうと、そのときに作り直しになる。

**やり直しの値段**: 器を先に作れば、モードの追加は分岐 1 つと、
切り替えレジスタを受ける口。器を作らなければ、`Y8960OPL2` 2 つの
メモリ保持を組み替えることになる。

**openMSX_Y8960 とは違う。** あちらは `<sampleram>256` をブロックごとに
持たせており、2 回路が別々の 256KB を見る（どの状態にも当たらない）。

`OpenMsxY8950LatestAdpcm` が RAM を自前で確保しているなら、
外から与える形に変える必要がある。**未確認**（該当箇所を読んでいない）。

**クロックは 3.579545MHz**（§3.3）。

**バックエンド切替の対象にはしない。** blueMSX+ の Y8950 は
`Y8950BackendBase` の下に複数実装を並べてユーザーが切り替えられる作りだが
（**確認済み(読解)**: `Y8950MultiBackend.h`）、Y8960 の OPL2 は 2 回路あり、
切替の器を 2 つ持つ意味が薄い。**独立したデバイスとして作る。**
OPLLEX を emu2413 1 本に決めた判断（§5.2）と揃えた。

**前提**: この判断は「Y8960 が WIP で、音質の比較検討より先に動くことが要る」
段階であることに依っている。仕様が固まって A/B 比較が要るようになったら見直す。
**やり直しの値段**: `Y8950BackendBase` を継承する形に変え、
`Y8950MultiBackend` に相当する器を Y8960 用に 1 本作る。デバイス側は変わらない。

### 5.2 OPLLEX（チャンネル別音色バンク付き YM2413）×2

**土台は `Src/SoundChips/Emu2413/` のフォーク**（2026-09-12 ユーザー決定）。

改造は 2 点。

| | 内容 |
|---|---|
| 音色テーブルを 4 面持つ | 現在の `opll->patch[19*2]` を `[4][19*2]` に広げる |
| チャンネルごとにバンクを選ぶ | `set_patch()` がそのチャンネルのバンクを見る。新設レジスタ 40h-48h の b1:b0 が BANK |

`set_patch()` は `MOD(opll,ch)->patch` / `CAR(opll,ch)->patch` にポインタを
向けているだけなので（**確認済み(読解)**: `emu2413.c:641-648`）、
向ける先をバンクで選ぶだけで済む。**構造上の障害は無い。**

#### **問題: emu2413 に YM2423 (OPLL-X) の音色データが無い**

**確認済み(読解)**: `emu2413.h:16` の `OPLL_TONE_ENUM` は
`OPLL_2413_TONE` / `OPLL_VRC7_TONE` / `OPLL_281B_TONE` の 3 つだけで、
`emu2413.c:35` の `OPLL_TONE_NUM` も 3。

Y8960 の OPLLEX は 4 バンクを要求する（`hardware-notes.md` §6 OPLLEX）。

| BANK 値 | 音色セット | 相当チップ | emu2413 に在るか |
|---|---|---|---|
| 0 | OPLL | YM2413 | **在る** (`OPLL_2413_TONE`) |
| 1 | OPLL-X | YM2423 | **無い** |
| 2 | OPLL-P | YMF281 | **在る** (`OPLL_281B_TONE`) |
| 3 | VRC7 | DS1001 | **在る** (`OPLL_VRC7_TONE`) |

調達先の候補。**どれも未確定**（§9.2）。

1. **`Src/SoundChips/NukedOPLL/opll.c` の `patch_ym2423`**（**確認済み(読解)**:
   同ファイル 189 行目に在る）。同じリポジトリ内で、ライセンスは GPLv2
   （**確認済み(読解)**: `NukedOPLL/LICENSE`）。`opll_patch_t` 構造体から
   emu2413 の 8 バイトダンプ形式への変換が要る
2. **openMSX_Y8960 の `YM2413NukeYKTBanked`** の音色データ。出所は
   "Copyright free OPLL(x) ROM patches" (David Viens / Hubert Lamontagne)、
   **CC BY-SA なので帰属表示が要る**

**ライセンスの注意**: emu2413 は MIT（**確認済み(読解)**: `Emu2413/LICENSE`）。
そこに GPLv2 のデータを入れると、**フォークしたファイルは GPLv2 になる**。
blueMSX+ 全体が GPLv2 なので配布上の問題は生じないが、
**Okazaki 氏の MIT 表示は残し、追加分の出所も併記する。**

**やり直しの値段**: 音色データ 1 テーブル（19 音色 × 8 バイト）の差し替え。
コードは変わらない。**先に決めなくても実装を始められる** — 1 バンクを
暫定で OPLL と同じにしておき、後で表だけ差し替えればよい。

### 5.3 SSGS（YMZ705/732 相当）×1

**土台は `Src/SoundChips/AY8910.c` のフォーク**（582 行）。

| | 内容 |
|---|---|
| レジスタ配置 | `$00-$1F` が SSG-1、`$20-$3F` が SSG-2。系統の選択は `(reg >> 5) & 1`。各系統内は `sub = reg & 0x1F` |
| `$0E-$0F` | **無い**。YMZ 系は I/O ポートを持たない（カートリッジ版の場合） |
| `$10-$12` | ch A/B/C の 4bit パンポット |
| 出力 | 1 つのステレオ・サウンドデバイス（6ch）。`mixerRegisterChannel(..., stereo=1, ...)` |

**クロックは 1.7897725MHz**（`3.579545 / 2`。§3.3）。本体 PSG と同じである。

**LED はSSG2 のレジスタ `2Fh` の下位 4bit**（§3.3）。
`hardware-notes.md`（写し）は旧 RTL に基づき `1Fh` と書いているが、
新しいレジスタ配置では `2Fh` になる。

パンポット値と L/R レベルの対応は**データシートに記載が無い**。
EPSGemuEngine（`src/YmzSsg.cpp`）と openMSX_Y8960（`Y8960SsgCore.cc`）は
同世代の YMZ280B と同じ分配則を採っている。**同じ則に合わせる**。
これは実装者の判断であって仕様ではない。

**AY コアの出力は片極性なので、パンを掛ける前に無音時レベル（直流成分）を
差し引く。** 省くと直流が定位に漏れる（出所: EPSGemuEngine のコメント。
openMSX_Y8960 も同じ処置をしている）。

**カートリッジ版はライトオンリー。** `ioPortRegister(port, NULL, write, ref)` で
読み出しを持たない登録ができる（**確認済み(読解)**:
`romMapperFMPAC.c:261-262` が 7Ch/7Dh でそうしている）。

**A0h / A1h が本体 PSG と重なる件は、上流を直して解決した**（§4.2）。
両方が登録でき、書き込みは両方に届き、読み出しは本体 PSG だけが駆動する。
**SSGS の着手を止めるものは無くなった。**

### 5.4 DCSG（SN76489）×2

**音源コアは blueMSX に既存**（`Src/SoundChips/SN76489.c`、650 行）。
2 インスタンスを作り、3Eh → DCSG 0、3Fh → DCSG 1 に載せる
（アドレス bit0 が回路を選ぶ。`hardware-notes.md` §7.1）。
1 バイト書き込みのみのレジスタラッチ方式なのでライトオンリー。

openMSX 側が `SNPSG` に足さず別デバイスに切り出した理由（イネーブラのゲートと
トンネルの入口が要り、既定値が他デバイスと逆になる）は blueMSX+ でも同じなので、
**`Src/Memory/romMapperY8960Dcsg.c` を別に作り、`SN76489` はコアとして呼ぶだけにする。**

**`sn76489Create` は署名の変更が要る。** 現在は `sn76489Create(Mixer*)` で、
ミキサー種別が `MIXER_CHANNEL_PSG` に、デバッガの表示名が `"SN76489 PSG"` に
固定されている（**確認済み(読解)**: `SN76489.c:226-227`。
同ファイル 485 行にもう一つ `sn76489Create` があるが、42 行目の `#if 1` /
376 行目の `#else` に挟まれた**死んだ側**である）。

Y8960 の DCSG は専用のミキサー種別（§6）に載せ、2 回路を区別できる名前が要るので、
**種別と名前を引数に取る形へ広げる**。既存の呼び出し側（ColecoVision / SG-1000 /
`SN76489.xml`）は既定値で通るようにする。上流ファイルに手が入るが、
openMSX_Y8960 も同じ理由で同じ変更をしている。

### 5.5 MSX-TIMER

**新規実装。** 移植元は openMSX_Y8960 の `src/sound/MSXTimer.cc`（517 行）。

| | 内容 |
|---|---|
| ポート | B0h = レジスタ番号、B1h = 値、B2h = 割り込みフラグ、B3h = カウンタ読み出し |
| 分解能 | Base Clock 85.909080MHz (= 3579545 × 24) を `2^(10+2r)` で分周。8 段 |
| 割り込み | `boardSetInt` / `boardClearInt`（**確認済み(読解)**: `Src/Board/Board.h:151-152`） |
| 時間の進め方 | `boardTimerCreate` / `boardTimerAdd`（同 211-213 行） |

**openMSX 側で踏んだ落とし穴を引き継ぐ**: カウント計算が 32bit を溢れると、
分解能 7・終端値 255 でカウンタが張り付く（openMSX_Y8960 の経緯 2026-09-10 (4)）。
**最初から 64bit で計算する。**

**イネーブラで閉じている間もカウンタと割り込みは動き続ける。**
実機のイネーブラが止めるのはアドレスデコードだけで、ブロックを停めるわけではない。

### 5.6 MSX-MIXER

**新規実装。** ただし openMSX 側とは作りが変わる。

§4.3 のとおり blueMSX のミキサーにはデバイス単位のゲイン API が無いので、
**各ブロックが自分の出力に自分で左右ゲインを掛ける。**
MSX-MIXER デバイスは、各ブロックが参照するゲイン値を保持する箱になる。

結線の方法は **未決**（§9.3）。openMSX 側は XML の id 参照で解決していたが、
blueMSX の `config.ini` にそれに当たる仕組みが無い。候補は次の 2 つ。

1. **プロセス内のシングルトン**。`romMapperTurboRTimer.c` が `theTimer` という
   static ポインタを持っているのと同じ形（**確認済み(読解)**: 同ファイル 53 行目）。
   Y8960 は 1 台しか挿さない前提なら成立する
2. **`deviceManager` から型で引く**。既存の API で引けるかは **未確認**

**B6h-B7h はゲインに繋がない**（openMSX 側と同じ）。B6h でレジスタ番号、
B7h でデータ、という入口までは作るが、**レジスタアレイの中身が未定**なので
値を憶えるだけにする。アドレス自体も暫定値である（`hardware-notes.md` §7.4）。

**出力の切り替え**（Y8960 だけ / 本体だけ / 両方）は openMSX 側に在る機能だが、
blueMSX+ でどう出すかは **未決**（§9.4）。

### 5.7 Y8960 SCC（バンクメモリ）

**土台は `Src/SoundChips/SCC.c`（既存）+ 新規マッパー
`Src/Memory/romMapperY8960Scc.c`。**

マッパーの規則は openMSX_Y8960 の implementation-plan §3.8.1 で確定している。
**その 4 規則をそのまま移す。**

| | 規則 | 出所 |
|---|---|---|
| 1 | SCC 音源レジスタは、その region 自身のバンクレジスタが 3Fh のとき、その region の 1800-1FFF に出る。**RAM モードのバンク0 だけは出さない** | openMSX 側の判断。**ファームウェアが使うのは BANK1 の 7800h だけ**なので、残る region は余分に出しているだけ（§3.3） |
| 2 | MMIO 窓は、**バンク1 が ROM を出しているときだけ**出る | **2026-09-12 にユーザーが確定**（§9.5） |
| 3 | RAM モードのバンク0 は書き込み不可 | openMSX 側の既存実装の踏襲 |
| 4 | バンク 3Fh を RAM バンクとして扱わない | バグ修正。`#16` 以上を RAM と判定すると `3Fh` も通ってしまう |

外に出る値は `hardware-notes.md` §3 / §4 と openMSX_Y8960 の §4.4 にある。

| 値 | |
|---|---|
| RAMMODE レジスタ | 48FBh（ミラー 49FBh-4FFBh） |
| RAM モードのバンクレジスタ | 48FCh-48FFh（同上） |
| 互換モードのバンクレジスタ | 5000-57FFh / 7000-77FFh / 9000-97FFh / B000-B7FFh |
| SCC 音源レジスタ | 各 region の 1800-1FFF |
| SCC 窓を開くバンク値 | 3Fh |
| MMIO 窓 | 7FE0-7FFFh（書き込み専用） |

**メモリ構成は決まった**（§3.3 / §9.5）。**256KB を 8KB × 32 バンクに区切り、
`#0`-`#15` が ROM、`#16`-`#31` が RAM。** MSSX のファームウェアがこれを前提に
動くので、RTL にバンク番号の分岐が無いのは WIP だからだと見てよい。

`y8960bas.rom` は 128KB = ROM バンク `#0`-`#15` にちょうど収まる。

窓の初期値は BANK0=`#0`, BANK1=`#1`, BANK2=`#2`, BANK3=`#3`
（**確認済み(読解)**: MSSX の `docs/y8960/hardware.md`。写しの §4 とも一致）。

**MMIO 窓は BANK1 に ROM バンクが出ているときだけ表に出る。**
RAM バンクまたは SCC (`3Fh`) のときは隠れる（§9.5。2026-09-12 にユーザーが確定）。
`rammode` を直接見ない。

### 5.8 I/O イネーブラとメモリマップド I/O のトンネル

この 2 つはブロックではなく、**Y8960 SCC のマッパーが持つ機能**である
（窓が 7FE0h-7FFFh にあり、マッパーがメモリ空間を見ているため）。

| 窓 | 内容 |
|---|---|
| 7FF6h | I/O Enabler 1。b0 = OPLL#1 (7Ch-7Dh)、b1 = OPLL#2 (7Ah-7Bh) |
| 7FFFh | I/O Enabler 2。b0/b1 = OPL2、b2/b3 = DCSG、b4 = SSG、b7 = MSX-TIMER |
| 7FEAh-7FF5h | 各ブロックへのトンネル。**イネーブラの影響を受けない** |

**窓そのものが出る条件は BANK1 の中身で決まる**（§9.5）。BANK1 に ROM バンクが
出ているときだけ表に出て、RAM バンクまたは SCC のときは**イネーブラごと隠れる**。
つまり **RAM バンクを BANK1 に出したままではイネーブラを書き換えられない。**

**リセット直後は全部閉じている**（openMSX 側の判断を踏襲。RTL は 7Ah 側と
A0h 側をリセット時有効にしているが、これは WIP のプレースホルダとして採らない）。

窓の中は**高位側が 1 番目**。直接 I/O 側とは並びが違う（`hardware-notes.md` §3）。
**片方から他方を推論してはならない。**

**イネーブラの実現方法は §4.2 を直したことで素直になった。**
ポートは重ねて登録できるので、Y8960 は自分の登録を常に持ったままにし、
**閉じているときは `writeIO` の中で書き込みを捨てる**だけでよい
（openMSX_Y8960 も同じ形にしている）。本体側が先に取っていても構わない。

`ioPortUnregister` でポートを出し入れする必要は無い。読み出しのある
ブロック（OPL2 と MSX-TIMER）は、閉じている間 `readIO` が `0xFF` を返せば
AND 合成で他のデバイスの邪魔をしない。

## 8. 検証方法

**ここが openMSX 側と最も違う。** ただし、**当初書いた「blueMSX+ には
自動テストの手段が無い」は言いすぎだった**。2026-09-12 に実測して分かった
ヘッドレスの経路を以下に含める。

openMSX_Y8960 は Tcl スクリプトで自動回帰テストを 13 本持っており、
どれも「期待値を外した構成で落ちる」ことまで確かめてある。
**blueMSX+ に同じことはできない** — エミュレータを走らせながら
レジスタを叩くスクリプト機構が無いため（**確認済み(読解)**:
`Src/Emulator/CommandLine.c:330-383` のオプション表に、スクリプトを実行する
手段も、音を録り始める手段も無い。`/debugger` はデバッガのウィンドウを
開くだけである）。

### 8.1 ヘッドレスで確かめられること

`/listromtypes` `/listmachines` `/listspecials` `/listthemes` は、一覧を
標準出力に書いて `exit(0)` する。**エミュレータのウィンドウが作られる前**に
終わる（**確認済み(読解)**: `Src/Win32/Win32.c` の `commandLinePrintLists` と
4892 行の `exit(0)`。**確認済み**: 実行してもプロセスもウィンドウも残らず、
終了コード 0 と出力が返った）。

| 手段 | Y8960 で何に使えるか |
|---|---|
| `/listromtypes` | **§6.1 の RomType 7 枠が登録されたか。**表示名と短縮名もそのまま出る |
| `/listmachines` | **7 ブロックを置いたマシン構成が読めるか。** `config.ini` をパースし、ROM ファイルの実在まで見る |

**`/machinedir` で作業ツリーの `Machines` を直接読ませられる**ので、
テスト用構成をコピーせずに試せる（**確認済み**）。

**Phase 0 の「器ができた」は、この 2 つで判定できる。**

### 8.2 ヘッドレスでは確かめられないこと

**デバイスの生成は走らない。** `machineIsValid` は `config.ini` のパースと
ROM の実在までで、`machineInitialize()`（`romMapper*Create` を呼ぶところ）には
届かない（**確認済み(読解)**: `Src/Board/Machine.c:647-690`）。

したがって次は**エミュレータを実際に起動しないと分からない**。

- **I/O ポートの登録が通ったか**（§4.2 の先勝ちで黙って落ちていないか）。
  これは Y8960 で最も危ないところなので、**起動しての確認が要る**
- 音が出るか、レジスタの挙動

| 手段 | 何ができるか | 未確認な点 |
|---|---|---|
| GUI で手動操作 | すべて。ただし人の手が要る | — |
| 音声ログ | `mixerStartLog()` が WAV を書く（**確認済み(読解)**: `AudioMixer.c:630`、UI からは `Actions.c:406`） | コマンドラインから開始する手段が見当たらない |
| MSX 側のテストプログラム | レジスタを叩いて結果を見る。BASIC 拡張やアセンブリで書く | 結果をホスト側へ取り出す経路 |
| デバッガプラグイン | メモリと I/O を覗く | 自動化できるか |

**起動するとウィンドウが出る。走らせる前に一声かけること。**

**非回帰テストの注意**（openMSX 側と同じ）: 修正後に通ることは、
**修正前に落ちることを示すまで証拠にならない。**
テストを書いたら、まず期待値を壊して落ちるのを確認する。

**実機が無いので「実機と一致」は検証できない。** できるのは
「openMSX_Y8960 と同じ挙動になること」までである。
openMSX 側は実測済みなので、**同じレジスタ列を与えて音を比べる**のが
最も確度の高い突き合わせになる。

### 8.3 最も強い検証 — ファームウェアを走らせる

**Y8960 を駆動する BIOS と拡張BASIC が実在する**（§3.3）。
madscient/MsxSoundSuiteExtension の `y8960bas.rom`、**128KB**。

**これは openMSX_Y8960 が持っていなかったものである。** あちらの
`hardware-notes.md` §8 は「BIOS ROM イメージが存在しない」と書いている
（hra1129/Y8960_Cartridge には無い、という意味では今も正しい）。

Y8960 SCC のマッパー（§5.7）が動けば、**この ROM を載せて起動できる**。
128KB は ROM バンク `#0`-`#15` にちょうど収まる。

**ファームウェアが起動して音が出れば、それは次のすべてが同時に通ったことを
意味する。**

- バンクレジスタと窓のデコード（§5.7）
- メモリマップド I/O のトンネル（§5.8）
- I/O イネーブラ（同上）
- 叩かれた音源ブロックそのもの

**どの単体テストより射程が広い。** 逆に、落ちたときにどこが悪いかは
分からないので、単体の確認と併用する。

**ただし起動が要るので、ウィンドウが出る**（§8.2）。自動で繰り返せない。

**ROM はリポジトリに入れない**（§3.1）。実機の BIOS ROM と同じく、
gitignore 済みのビルド出力に置く（`doc/fork/build/README.md` §4）。

**前提**: MSSX 側も開発中である。Y8960 BASIC Extension と
Y8960 Sequencer BIOS は「（開発中）」と明記されている（**確認済み(読解)**:
MSSX の `README.md`）。**動かないときに、こちらが悪いとは限らない。**

### 9.5 SCC バンクメモリ — **決着済み（2026-09-12）**

§5.7 / §3.3。MSSX の記述と、**2026-09-12 のユーザーからの直接の回答**で
すべて決まった。**未決は残っていない。**

| | 決まったこと |
|---|---|
| ROM / RAM の境界 | **256KB、`#0`-`#15` が ROM、`#16`-`#31` が RAM。** ファームウェアがこれを前提に動く |
| SCC 窓 | **BANK1 に `3Fh` を書くと `7800h` に出る。** ファームウェアはここを使う |
| **MMIO 窓の出現条件** | **BANK1 に ROM バンクが出ているときだけ表に出る。RAM バンクまたは SCC のときは隠れる** |

**ROM 128KB + RAM 128KB の分割が正しい。** RTL にバンク番号による分岐が
無いのは、RTL が WIP だからだと見てよい（§2 の前提と整合する）。
**openMSX_Y8960 の既存実装（分割して持つ）が実機の意図に合っていた**ことになる。

blueMSX+ は**この境界で新規に書く**。openMSX 側が保留にしていた #2/#3/#5 は、
blueMSX+ では迷う必要が無い。

#### MMIO 窓の条件は BANK1 の中身だけで決まる

**2026-09-12 にユーザーから直接の回答があった**（最も強い出典）。

> BANK1 の MMIO は ROM が選択されている場合のみ表に出る。
> RAM または SCC が出ている時は MMIO は隠れる。

**`rammode` を直接見ない。** 見るのは BANK1 のバンクレジスタが何を指しているかだけ。

| BANK1 の中身 | MMIO 窓 |
|---|---|
| ROM バンク（`#0`-`#15`） | **出る** |
| RAM バンク（`#16`-`#31`） | 隠れる |
| SCC（`3Fh`） | 隠れる |

**これは openMSX_Y8960 の規則 2 と一致する**（あちらの §3.8.1 が
`!(ramEnabled && isRamRegion(3)) && bankreg1 != 3Fh` と書いている）。
**両者の挙動は割れない。**

**MSSX の文書を「RAM モード 0 のとき**または**BANK1 に ROM」と読んだのは
誤りだった**（本書が 2026-09-12 に一度そう書いた）。RAM モード 0 であっても、
BANK1 が RAM バンクや SCC を指していれば MMIO は隠れる。

**前提**: MMIO 窓のアドレスが `7FE0h`-`7FFFh` から動かないこと。
動けば SCC 窓 `7800h`-`7FFFh` との包含関係が崩れ、条件が書き直しになる。

### 9.6 ミキサーの音量スライダをどこに出すか

### 9.7 2 回路を 1 デバイスにするか 2 デバイスにするか

OPLLEX / OPL2EX / DCSG は 2 回路ある。

- **1 デバイスが 2 回路を持つ**と、マシン構成に 1 行置けば 2 回路そろう。
  片方だけ載せる構成が作れない
- **2 デバイスを別々に置く**と、1 回路だけの構成が作れる。
  `config.ini` に 2 行書くことになり、`RomType` も 2 つ要る（§6.1 の表が変わる）

**「個別にマシン構成に追加できるようにする」という指示は、
ブロック単位を指していると読んだ**（ユーザーが挙げた一覧が回路単位ではなく
ブロック単位だったため）。§6.1 は 1 ブロック 1 `RomType` で組んである。
**回路単位まで分けたいなら、`RomType` を決める前に言ってほしい**（§6.1 の
値段はここが一番高い）。

### 2026-09-12 (5) — ADPCM の RAM は 4 状態をとる

**2026-09-12 にユーザーから直接の回答があった。**

256KB を 2 回路でどう分けるかに **4 状態**ある（共有 / 片寄せ ×2 / 分割 128+128）。
**設定の方法は実機側で未実装**で、**暫定として起動時は共有モード**と置く。
ハードウェア側で決まり次第、修正する。MSSX も共有モードで動く前提。

写しの §7.5 が「manual にあるがレジスタが無い」と書いていたのは、
この状態を指していたことになる。**エミュレータ側で先に決めても、
突き合わせる相手がまだ無い。**

**器は 4 状態ぶん作る**（§5.1）。実装するのは共有モードだけだが、
サンプル RAM を回路の外に 1 つ持ち、各回路が見る範囲をモードで決める形に
しておく。回路ごとに RAM を持たせると、切り替えが決まったときに作り直しになる。

**openMSX_Y8960 はどの状態にも当たっていない。** `<sampleram>256` を
ブロックごとに持たせているので、2 回路が別々の 256KB を見ている。


### 2026-09-12 (4) — MMIO 窓の条件が確定し、誤読が 1 件見つかった

**2026-09-12 にユーザーから直接の回答があった。**

> BANK1 の MMIO は ROM が選択されている場合のみ表に出る。
> RAM または SCC が出ている時は MMIO は隠れる。

**§9.5 に残っていた最後の 1 点が解けた。SCC バンクメモリに未決は無い。**
見るのは BANK1 のバンクレジスタが何を指しているかだけで、`rammode` は
直接には効かない。

**訂正**: 本書は同日、MSSX の「RAM モード 0 のとき、または BANK1 に ROM
バンクが出ているときにしか現れない」という文を**2 条件の or と読み**、
RAM モード 0 で BANK1 が SCC のときに両者が食い違うと書いた。**誤読だった。**
条件は 1 つで、BANK1 の中身だけで決まる。

**結果として openMSX_Y8960 の規則 2 と完全に一致した**
（`!(ramEnabled && isRamRegion(3)) && bankreg1 != 3Fh`）。
**両者の挙動は割れない。** あちらが「RTL の `~rammode` の置き換え（判断）」
として書いた条件は、判断ではなく仕様どおりだったことになる。

**副次的に分かったこと**: BANK1 に RAM バンクを出したままでは
I/O イネーブラを書き換えられない（窓ごと隠れるため）。§5.8。
